# Правила пользователя

Обязательны для любого агента (главной сессии и субагентов). Каждое правило появилось после конкретного случая — причина
записана, чтобы правило применялось по смыслу, а не по букве. Где правило исполняет код, это сказано: обходить такую
проверку нельзя, даже если «очень надо» (`lab.toml [isolation] enforce = false` меняет только пользователь).

Формат: **правило** → *почему* → как применять.

## 1. Принуждение: движок, ввод, экран

### 1.1. Ввод ОС запрещён; движок агентами — только тестовой сборкой `--f2f`
*Почему.* Пользователь работает за этим ПК во время тестов. Один агент двигал мышь и перехватывал фокус скриптом
(`mouse_event`/`SetForegroundWindow`), чтобы «доказать» поворот мыши; другой запустил стоковое окно движка для замера fps —
оно захватило курсор пользователя и открывало паузу при смене окна. Слова в заданиях не помогли дважды, поэтому правило
исполняет софт.

Исполняет `vclab/policy.py`: вид экземпляра с exe движка (`voxelcore*`) запускается только с `--f2f`; после первого `hello`
демон сверяет `hello.flags.input == "isolated"`, `flags.clock` и `hello.version` = `f2f_version` движка аренды. Не совпало —
дерево процессов убито, ошибка `isolation-failed` / `engine-mismatch`.

Как применять:
- движок — только арендой (`lab lease`, `lab run`, MCP `vc_start` = аренда `vc.dev`); свои exe-копии, порты, `Start-Process`,
  `Stop-Process -Name` — нет;
- ввод — только F2F `input`/`gui` (CLI `lab f2f`, MCP `vc_input`). Он попадает в то же состояние `Input` движка, что и
  настоящий ввод, поэтому это честная проверка обычного пути кода;
- никаких `SendInput`, `keybd_event`, `mouse_event`, `SetForegroundWindow`, `vc_keys`, `vc_click` (в MCP они отключены) — ни
  «для ручной проверки», ни в пробах. Пробам окна — только `SW_SHOWNOACTIVATE` / `SW_SHOWMINNOACTIVE`;
- то, что проверяется только человеком у настоящего окна, — описать и оставить пользователю;
- каждое задание субагенту, который трогает движок, повторяет этот запрет явно.

### 1.2. Стоковый `VoxelCore.exe` — только пользователю
*Почему.* «Рантайм только для меня и тебя как финальная проверка по запросу или релизу, разово, а не по 10600 раз». Стоковое
окно принимает настоящий ввод. Однажды агент по заданию «оценить нативные возможности 0.32» один раз открыл стоковое окно —
и на 0.45 с забрал фокус.

Исполняет `policy.check_runtime_lease`: вид `role = "runtime"` создаётся только сеансом `lab play`:
- `lab play <проект> --user` — владелец `user`, только из интерактивного терминала пользователя (не MCP, не скрипт);
- `lab play <проект> --final-check --reason "..."` — главная сессия (`claude`) или пользователь, разово, с причиной; запись
  `runtime_session` в истории.

Стоковый exe любой версии в тестовом (оконном) виде — отказ `policy` (403). Без окна (`role = "headless"`, `--headless`) —
можно: такой процесс физически не принимает ввод; демон всё время его жизни проверяет, что у дерева нет окон.
Субагентам и циклам замеров стоковое окно — никогда. Не писать агентам «запусти сток, посмотри»: нативные возможности
оценивать чтением кода, headless-прогоном или через F2F-сборку.

### 1.3. Тесты не зависят от Windows
*Почему.* Фокус, перекрытие окон, случайное нажатие пользователя не должны менять результат («надёжное и серьёзное
решение», а не «по возможности»).

Как применять: снимок — только из кадрового буфера (F2F `shot`, FBO фиксированного размера), не захват окна; `normal` и
`hidden` побайтно равны. Результат паритета, полученный через захват окна (PrintWindow `vc_screenshot` в запасном режиме,
пиксели окна), тестом не считается.

### 1.4. Экземпляры агентов немые
*Почему.* Тестовые движки агентов «протекали звуком» в Windows.

Как применять: в каталоге аренды (`--dir` = каталог экземпляра) — свой `settings.toml` с `[audio] volume-master = 0`
(или `enabled = false`, если проекту не нужен живой звуковой бэкенд). `settings.toml` пользователя не трогать. **Ядро этого
пока не проверяет** — пишет проект (шаг `prepare` вида); вид `vc.dev` работает с `--dir <work_root>\vc_dev` — его звук
отключайте настройками рантайма только по согласованию с пользователем.

### 1.5. Кадр тестов — 854×480
*Почему.* Агенты гоняли движки с разными окнами, сравнения расходились «из-за стандарта».

Один размер для всех агентов и сценариев (`[scenario] default_size`, `f2f/PROTOCOL.md` §8). Другой — только явно в поле
`"size"` сценария и сразу для обеих сторон сравнения; снимки разного размера харнесс не сравнивает. Размер не задаётся
в личном лаунчере агента.

## 2. Общие ресурсы: движок, демон, процессы, диск

### 2.1. Движком владеет один агент
*Почему.* Два агента дрались за движок: закончивший агент продолжал его останавливать, у другого рушились команды;
пользователь смотрел на бесконечные перезапуски.

Как применять: в задании агенту явно — «движок у тебя» или «движок не запускать». Агентов, которым нужен движок, — по
очереди: следующий получает его после того, как предыдущий отчитался и остановлен. Закончивший агент, который продолжает
действовать, — работающий процесс: остановить (`TaskStop`), а не писать ему.

### 2.2. Демон общий, как движок
*Почему.* Субагент перезапустил демон ради своей правки ядра, пока у другого агента было пять живых аренд и прогон:
Job Objects убили чужую сессию целиком. «Надо не допустить и предотвратить на будущее».

Исполняет `vclab/daemon/admin.py`: операции уровня демона (`lab daemon stop|restart|upgrade|drain|undrain|reload-core`,
`lab release --all --force`, `lab gate accept`, `lab golden promote`) — только роль `admin` (`[roles] admins`, по умолчанию
`user`, `claude`); немедленная операция при чужой аренде — `foreign-leases`, при живых — `live-leases`; всё в аудите.

Как применять:
- субагент работает с `LAB_OWNER=<имя> LAB_ROLE=agent` (CLI) или `owner=<имя>, as_agent=true` (MCP-мост общий с главной
  сессией и без этого ходит от имени `claude`);
- правки `vclab/` и `lab.toml` проверять на своём изолированном демоне (`lab daemon start --isolated`, порт 25800–25849) и
  сдавать главной сессии; применяет admin: `lab daemon upgrade` (drain: новые аренды не выдаются, ждём конца живых);
- `lab.toml`/ядро «на живую» не менять.

### 2.3. «Стоп» пользователя = остановить всё сразу, в том же ответе
*Почему.* На «стоп» агент отвечал письмами субагентам и просьбами о паузе, пока пользователь не закричал: «ты не слушался
вообще».

Как применять: «стоп», «останови», «прекрати» или явное раздражение тем, что что-то работает, — немедленно: `TaskStop`
каждому агенту, `lab release --all --force` (admin) и/или `vc_stop`, затем отчёт, что остановлено. Никаких сообщений
агентам, «пауз» и вопросов.

### 2.4. Ничего не убивать и не удалять без ведома пользователя
*Почему.* Пользователь заметил, что тают место на SSD, память и CPU, и попросил найти, кто что оставил: «НИЧЕГО НЕ КИЛЯЙ БЕЗ
МОЕГО ведома».

Как применять: при подозрении на лишнюю нагрузку — сначала опись (процессы Windows и WSL с CPU/RAM и кому принадлежат,
`lab ps --table` с `foreign`, рост диска: каталоги сборок, изолированные демоны, прогоны) и отчёт; убивать и удалять —
только после слова пользователя. Исключение — его «стоп». Чужие процессы движка демон сам никогда не убивает (сторож только
показывает `foreign`). Чужие аренды не трогать (`not-owner`).

### 2.5. Убирать только своё — и всё своё
Каждый агент в конце: `lab release` своих аренд, `lab --daemon P daemon stop` своего изолированного демона, удаление своих
временных файлов. Ничего не оставлять работающим или растущим (движки, демоны, серверы, `cargo`).
*Почему диск важен.* Диск WSL (`ext4.vhdx`) сам не сжимается: удалённое внутри WSL место на диске Windows не возвращается.
Четыре агента со своими `CARGO_TARGET_DIR` (по 2.5–8 ГБ) и черновик замеров (3.4 ГБ) «съели» десятки гигабайт. Поэтому:
общий каталог сборки (`target`, не `target-<имя>`), временное — в scratchpad задания, крупные удаления — сообщать.

### 2.6. Не больше двух субагентов одновременно (временно)
Ограничение пользователя на число одновременно работающих субагентов, а не экземпляров движка: экземпляров демон
выдаёт столько, сколько позволяют ресурсы ПК. Суть правила — в чистых замерах: кому нужен замер (`lab perf`,
ворота производительности), тот ждёт свободный ПК, занятый прогон помечается `contended` и в сравнения не идёт.
Лимит на двух субагентов — временный, пока волны идут на одном ПК; пользователь снимет его отдельно.

### 2.7. Субагенты — только модель opus и ниже
*Почему.* Главная сессия — на старшей модели, она дорогая, недельный лимит уже упирался. Работа субагентов (порты, тесты,
документы) её не требует. Каждый вызов агента — с явной моделью (`opus`, для мелочи — ниже), не по умолчанию.

## 3. Измерения и доказательства

### 3.1. Замеры — только на свободном ПК
*Почему.* Агенты снимали fps, пока шли чужие движки, Java-серверы и пользователь работал; несколько отчётов пришлось
помечать «ПК был занят». Это должно быть свойством софта, а не привычкой.

Исполняет `lab perf` (`vclab/quality/perf.py`): ждёт простоя (`[perf]` в `lab.toml`: 30 с подряд, не дольше 600 с; чужие
движки/Java, CPU посторонних, GPU, ввод пользователя, другие работы лаборатории), не дождался — отказ (код 4); занятость во
время прогона — `contended`, такие прогоны не идут в ворота и сравнения. Как применять: замеры — только `lab perf`; рядом с
каждым числом — состояние загрузки; пока другой агент держит аренды движка, перф не гонять (пиксельные прогоны — можно:
пиксели от загрузки не зависят, но их тайминги — не перф).

### 3.2. Замеры сверять с записями
*Почему.* Субагент заявил «Bytearray быстрее» по одному замеру; пользователь помнил прошлые цифры и назвал это выдумкой —
сверка показала, что выигрыш дала другая правка.

Как применять: прежде чем сказать «X быстрее/медленнее», найти записанные замеры (README/OPTIMIZATION паков, документы
проекта, `lab history`) и привести новые числа рядом со старыми. Расхождение — сначала объяснить (другой хост, лок кадров,
виртуальные часы против реального времени, вывод на экран), потом выводы. Пример: Doom 120 fps старого пака — виртуальные
часы (игра быстрее реального времени), 70 fps порта — реальное время, 35 тиков × 2 кадра; это не регрессия.

### 3.3. Не торопиться; утверждение — с выводом
«НЕ ТОРОПИСЬ». Каждое «работает/сломано/быстрее» подкрепляется выводом команды, числом, путём к прогону или снимку. Чего не
проверял — так и написать. Прежде чем чинить «регрессию», убедиться, что это не ожидаемое поведение (см. `LESSONS.md`).

### 3.4. Поведение VoxelCore проверять запуском движка
*Почему.* Агент предсказал отказ по чтению stdlib и прогону в обычном `luajit`; пользователь: «всё там работает так, как
работает, по причине». VoxelCore-Lua отличается от стокового (свой `bit` с `compile`/`execute`, обёртка `error`,
`Bytearray` на FFI, свой `package.loaded`, нет `ffi` у паков...).

Как применять: смотреть, как это сделано в существующих паках, дампить реальное окружение (`_G` и нужные таблицы), запускать
в движке — `lab run vc <файл.lua>` (headless `--test`), аренда F2F-сборки. Обычный `luajit` доказывает только поведение Lua
вообще.

## 4. Движок, каталоги, файлы пользователя

### 4.1. Движок пересобирать можно, менять — только для F2F
*Почему.* «Я запрещаю модифицировать что угодно кроме штук для frame2frame pixel2pixel тестирования и автоматизации». Игра,
рендер, освещение, API для логики — паками, Lua, шейдерами, ассетами на стоковом движке.

Как применять: правки движка — только шаг кадра, снимок, синтетический ввод, изоляция, дампы состояния, сиды (`f2f/`);
маленькие, в своих файлах или помеченных блоках; каждую называть в отчёте. Проблема порта «требует правки движка» — сначала
искать решение паком (переопределение шейдера, `world.set_chunk_data`, canvas, XML-фреймы), иначе спросить пользователя.

### 4.2. Сборка движка — релизным рецептом
*Почему.* Сборка MSVC из пресетов дала другой LuaJIT (2.1.0-beta3 против коммита релиза) — «такие различия не должны
существовать вообще: проект собран так, как .exe релиза оригинала».

Как применять: тот же тулчейн, что у CI релиза (MSYS2 CLANG64, vcpkg `x64-mingw-static`, тот же снимок vcpkg → тот же LuaJIT),
статическая линковка; равенство доказывать `--version`, `jit.version`, дампом окружения (`f2f/tests/env_dump.lua`), списком
импортов DLL (`f2f/README.md`). Не воспроизводится — сказать и спросить.

### 4.3. Каталог движка — только рантайм
*Почему.* Агент завёл сборочные исходники и скрипты в каталоге установки движка: «сборки в этом движке нет».

В каталоге рантайма (`engines_root`, `<work_root>\vc_dev`) — только паки, сгенерированные модули, сценарии. Исходники, сборка, wasm,
upstream — в своих репозиториях. Исключение — справочные репозитории, которые туда положил сам пользователь.

### 4.4. Миры и файлы пользователя не трогать; оригиналы не удалять и не переносить
Миры, `settings.toml`, `config:`, файлы вне репозитория — только читать; тесты — на копиях (prepare `copytree` в каталог
аренды). Перенос — копированием: оригинал остаётся на месте, пока пользователь не скажет иначе. Пользовательские
`latest.log`/логи копировать до своего запуска (лог перезаписывается).

### 4.5. `.bak` — не внутри паков
Всё, что лежит в каталоге пака, — контент: движок его сканирует, манифесты паков и zip «другу» его раздают. Резервные копии
держать вне каталогов паков.

### 4.6. Коммит и пуш — только по просьбе
Коммитить и пушить, когда пользователь попросил. Пуш — от его имени (`gh`, аккаунт `lookibed`), без `--force` и без
перезаписи чужих коммитов. Ветки F2F — в приватный `lookibed/voxelcore-f2f` (remote `private`); `origin` исходников движка —
upstream, туда не пушить.

## 5. Как работать

### 5.1. Файл прогресса на диске
Сеть у пользователя нестабильна, сессия может оборваться, агент — умереть без отчёта. Долгая задача ведёт файл прогресса в
репозитории или scratchpad (что сделано, что дальше, пути, числа) и обновляет его после каждого этапа; файл — в
`.gitignore`, если не просили иначе.

### 5.2. «Целесообразность не наш конёк»
Пользователь исследует, что технически возможно (Java → wasm → Lua, растеризация в UI-шейдере, LLM на GPU пака). Нестандартный
путь не отвергать «из практичности»: назвать реальные препятствия с доказательствами и предложить самый маленький
эксперимент. Прежде чем объявить «движок не умеет», посмотреть паки пользователя и исходники движка — как это уже сделано.

### 5.3. Не ухудшать умолчание ради технического пути
Путь, требующий меньшего разрешения или качества, — опция для замеров; умолчание — полное качество («мыло» вместо
нативного разрешения пользователь отверг). Менять то, что пользователь видит по умолчанию, — только с его согласия.

### 5.4. Паки при разработке запускать напрямую, не кликами по меню
Пункт меню движка «Сценарии» — вход для пользователя при сдаче. Во время работы пак/страница/мир открываются сразу при старте
стартовым сценарием (`vc_start(script=...)`, `prepare` вида со стартовым скриптом). Общую логику держать в модуле пака, чтобы
меню и прямой запуск не расходились; пункт меню проверить один раз перед сдачей (кликом F2F).

### 5.5. UI — инструментами с состоянием, без слепых ожиданий
*Почему.* Агент ждал экранов с таймаутами по 30–300 с, пользователь кликал за него; потом агент шесть раз прошёл один и тот же
путь меню руками. Это должно быть свойством инструментов: каждое действие журналируется с временем и снимком, повторяемый
путь — сценарий, затык виден в отчёте.

Как применять: ждать условием (`lab f2f`/шаги сценария `wait`, MCP `vc_wait_log`, `scenario_run`), не `sleep` и не
повторными опросами; повторяемый путь — сценарием (`lab run`, MCP `scenario_save`/`scenario_run`); после серии действий —
`journal_report`. Шаблон ожидания сначала проверить на существующем логе.

### 5.6. Ядро не знает проектов
Инфраструктура (демон, аренды, интерпретатор, golden, история, перф, MCP) — общая для всех проектов; всё про конкретную
игру — в `projects/<имя>/` (плагин, дескриптор, сценарии). Задание на правку ядра говорит это явно, а приёмка показывает
второй проект на тех же инструментах (`docs/PROJECTS.md`).

### 5.7. Начало сессии
Прошлая сессия могла оборваться: агентов не возобновить, на диске — недоделанное. Сначала `git status` репозиториев,
`lab ps --table` (свои мёртвые аренды — освободить; чужие — не трогать), файл прогресса прошлой задачи; незнакомые правки не
собирать вслепую (`docs/ONBOARDING.md` «Начало сессии»).

## 6. Что писать в задании субагенту
Владелец движка или нет; `LAB_OWNER=<имя>`, `LAB_ROLE=agent` / `owner, as_agent=true`; запрет ввода ОС и стокового окна;
демон общий — `stop/restart/upgrade` нельзя, ядро — на изолированном демоне; каталог сборки (общий, не свой); что убрать за
собой; файл прогресса; модель `opus` и ниже; что вернуть: цифры, пути прогонов, что проверено чем, что не проверено.
