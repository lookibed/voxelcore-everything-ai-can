# Olife: производительность такта мира (волна 5p, 02.10, агент olife_w5p)

Вопросы: исполняется ли код мира под JIT; из чего состоит такт мира `content/olife_world` и откуда всплески p95/max;
какие конструкции рвут трассы LuaJIT; что безопасно исправить. Движок не менялся (стоковый 0.32 headless, LuaJIT
**2.1.1788856981** — сборка vcpkg `c6ffc141`, исходник `D:\Prog\AlphaMine\engine\vcpkg-032\buildtrees\luajit`).

## 0. Итог
- **Код мира компилируется JIT-ом**: `jit=off` даёт такт под `olife_sandbox_load` 124.6 мс (p50) против 10.5–11.0 мс,
  мир не держит 20 Гц. Bytearray (FFI) без JIT в 130–250 раз медленнее, `pcall` в 35 раз.
- **Но со стоковыми лимитами LuaJIT кэш трасс переполняется**: `maxtrace=1000`, а мир + base-пак движка (`grass_block`,
  `mob`, `events`) требуют ~1450 трасс. Кэш сбрасывается целиком (`flush`) 17–18 раз за 25 с, за прогон
  перезаписывается ~20 000 трасс. Это и есть главная причина всплесков (max 71–86 мс) и «snapdelta в 10 раз дороже
  стенда»: тот же стенд со сбросом кэша раз в 28 тактов — 0.952 мс/такт против 0.032 (дороже, чем вовсе без JIT, 0.673).
- Вторая причина всплесков — **сборка мусора внутри такта**: 3.3 МБ мусора за такт (TickInput 2.0 МБ, TickResult
  1.1 МБ), цикл GC завершался внутри фазы примерно каждый второй такт, атомарная фаза и sweep дают +5 мс.
- Исправления (паритет не менялся, весь регресс olife зелёный, §5): `jit=tuned` по умолчанию, −1.6 МБ мусора за
  такт, ключ чанка без массивной части, FNV без ветки, плоский обход сетки вида, GC после такта.
  **`olife_sandbox_load`: такт p50/p95/max 10.97 / 26.03 / 71.04 → 6.08 / 6.71 / 9.98 мс, mean 13.89 → 6.14**
  (+ 2.9 мс GC после такта, в простое периода 50 мс). **`olife_load`: 1.24 / 2.59 / 12.04 → 1.03 / 1.29 / 1.72 мс,
  mean 1.55 → 1.04** (запись волны 2 до сетевого кода 4c: avg 1.08, p95 1.47, max 2.32).

  `gc=tick|auto`, `gcbudget=<мс>`, `gcmax=<МБ>`, `gcpause`, `gcstepmul`; профиль — `prof=1`, журнал трасс — `jitlog=1`.

  тактами, время движка между тактами (`gap`), события такта (кадры, чанки, ключевые кадры снимков, TickResult
  применено/опоздало, циклы GC, события трасс). Часы — `time.precise_time` (steady clock, шаг 0.1 мкс, вызов ~40 нс,
  проверено `tools/olife/tests/probe_jit.lua`); `os.clock` в 0.32 шагает по 1 мс.

- **Условия**: все A/B ниже — сценарии `lab run` подряд (14:07–14:39), `lab sysload` перед сериями — простой, но это не

**Причины всплесков** (такты ≥ p95 против остальных, `prof_summary.json → spikes`):
1. **Сброс и перезапись трасс** (сток): в каждом такте окна были события трасс; избыток на всплесках — `sb_decode`

   `sb_decode` +23…+52 мс при 250–580 событиях трасс за такт; такты 286–306, 366–371, 645–650 — сразу после сбросов.
2. **GC внутри такта** (`tuned`, без сбросов): все 26 всплесков — такты, где куча уменьшилась внутри (`gc_in_tick` 1.0
   против 0.40 у остальных), избыток — фаза, в которой закончился цикл: `si_view` +5.2 мс, `sb_decode` +1.3.
3. **Не причины**: ключевые кадры снимков (`keyframe` 11.5 % всплесков у стока — это фон 1.5 % × сбросы, у `tuned` 0 %),
   отправка чанков (0 %), запоздавшие TickResult (23 % всплесков у стока — следствие: медленный такт → два результата в
   следующем; у `tuned` 0 %).

## 6. Бэклог (по ожидаемому выигрышу)
1. **Разбор TickResult** (`sb_decode` 1.3 мс, 871 КБ/такт): сгенерированный декодер создаёт таблицы на сущность, метр,
   каждое действие и Vec3; `r_str` — `utf8.tostring(slice)` (новый Bytearray на строку). Режим генератора «в плоские
   поля/переиспользуемые таблицы» для горячих сообщений (`TickResult.entities`) — ожидаемо −0.7 мс и −0.6 МБ/такт.
2. **`si_view` 1.15 мс**: `tostring` чисел (5 на сущность) — главная цена; позиция сущности меняется каждый такт, но
   фрагмент можно строить из квантованных значений или кэшировать по (x, y, z); типизированный вид в `sandbox.yaml`
   вместо JSON (уже в бэклоге OLIFE.md п.2) убирает склейку совсем — ожидаемо −1 мс и разбор JSON у сервиса.
3. **`r_terms` 0.58 мс** (хэш 7 чисел × 4 байта арифметикой double на каждую сущность каждый такт): считать только для
   сдвинувшихся сущностей или перейти на хэш по 32-битным словам (`bit` вместо `%`) — изменение протокола (клиент считает
   то же), версия схемы. Ожидаемо −0.4 мс при 500 движущихся.
4. **`w_rehash` 0.4–0.5 мс** — не FNV (0.009 мс на чанк), а `world.get_chunk_data` (кодирование чанка в движке,
   ~0.2–0.5 мс на чанк, `bench_w5p_rehash.lua`). Реже (1 чанк за такт / раз в 2 такта) — дольше видны чужие изменения;
   решать вместе с тестом `olife_blocks`.
5. **`w_str` → `Bytearray(v)` на каждую строку** (`wire.lua:125`, шаблон генератора) — FFI malloc на строку (500 видов
   TickInput за такт) и вклад в счётчик 50 МБ, после которого аллокатор Bytearray зовёт `collectgarbage("step", 200)`
   внутри такта. Писать строку в буфер без промежуточного Bytearray (нужен API движка или побайтно с JIT) — −0.2 мс и
   реже принудительный шаг GC.
6. Мелочи: компаратор `scripted()` вынести из функции (`sandbox.lua:47`), `table.sort` в `update_interest` (`server.lua:486`),
   замыкания в `M.apply` (`sandbox.lua:239`).
7. `gc=tick` держит GC в простое периода; при такте > ~40 мс бюджета не останется — тогда `gcbudget` меньше или
   `gc=auto`. Защита `gcmax` (512 МБ) возвращает автоматический GC.
