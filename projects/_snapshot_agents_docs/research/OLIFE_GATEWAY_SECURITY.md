# Olife: разбор безопасности рукопожатия шлюза (волна 3c, 02.10, olife_w3g; статус — волна 4b, §7)

> **Статус (волна 4b, 02.10, olife_w4b):** п.1 из §6 сделан — долгий токен больше не идёт в игровой сокет: клиент
> обменивает его по HTTPS (запрос запечатан к закреплённому x25519-ключу) на одноразовый билет ≤ 60 с, шлюзы (Rust и
> `gateway_dev.py`) проверяют билет офлайн. Подробно и с цифрами — §7. Остальное в §6 (Noise, TLS, QUIC, mTLS к миру) — нет.

Объект: рукопожатие клиента и канал шлюз→мир у `gateway_dev.py` (эталон) и Rust `olife-gateway` (`/root/olife/gateway`,
`D:\Prog\Olife\gateway`). Протокол — `tools/olife/protocol/{client,internal}.yaml` v1. Клиент — пак VoxelCore 0.32:
в его Lua есть HTTPS (`network.get/post`, curl с `verify_ssl`), но игровые сокеты только открытые TCP/UDP
(`network.tcp_connect`, `udp_connect`; TLS нет, `doc/en/scripting/builtins/libnetwork.md` 0.32). Это главное ограничение.

## 1. Как сейчас
`Hello{proto, name, token, engine}` — первый кадр, открытым текстом. Шлюз: токен → аккаунт (файл или supervisor
`GET /sup/auth?token_sha=<sha256>`), баны, имя, мир готов → `Attach`. Дальше keepalive: `KeepAlive{challenge}` раз в 2 с,
ответ с тем же числом, 10 с тишины = код 6. Канал к миру — одно TCP-соединение, `GatewayHello{secret}` открытым текстом.

## 2. Повтор (replay)
| угроза | сейчас | оценка |
|---|---|---|
| перехват токена в сети (общий Wi-Fi, провайдер, ретранслятор) | токен — статический bearer в `Hello`, без срока и привязки к соединению | **высокий**: увиденный один раз токен входит сколько угодно |
| повтор записанного `Hello` | ничего не связывает `Hello` с моментом/соединением | то же самое |
| «кража» сессии через вход с тем же токеном | дубль (то же имя+аккаунт) выбивает **старую** сессию (код 12) | злоумышленник с токеном может выбивать игрока бесконечно |
| keepalive challenge | только проверка живости; не аутентификация | `gateway_dev.py` берёт `random.getrandbits` (MT19937, предсказуем после 624 значений) — в Rust `getrandom` (CSPRNG). Последствие — лишь подделка живости |
| канал шлюз→мир | секрет открытым текстом, без nonce | на localhost приемлемо; между машинами — повтор `GatewayHello` даёт полный доступ к миру |

## 3. Тайминги
- **Сравнение токена.** `gateway_dev.py`: `dict.get(token)` по открытому токену — хэш строки + сравнение с кандидатами в
  корзине (memcmp), теоретический оракул совпадения префикса при коллизиях; через сеть практически не измерим, но не ноль.
  Rust: SHA-256 от предъявленного токена → поиск в `HashMap` по дайджесту (+ сравнение дайджеста за постоянное время,
  `auth::ct_eq`). Атакующий управляет токеном, но не байтами дайджеста — оракула нет. Supervisor: поиск по индексу
  `token_hash` в SQLite — то же свойство. Админ-токен HTTP (`X-Admin-Token`) — тоже `ct_eq`.
- **Разные исходы различимы по коду** (4 плохой токен / 5 бан / Welcome) — это сознательно (клиенту нужна причина), а
  значит перебор токенов ограничивается только частотой. `gateway_dev.py` не ограничивает неудачные входы вообще; Rust:
  ведро неудач на IP (20/мин) → временный бан IP на 30 с, плюс лимит соединений на IP (64 одновременно, 20/с, всплеск 60)
  и на шлюз (4096). Коды неудачной попытки не меняются (негативные тесты те же).
- Энтропия: dev-токены (`olife-dev`, `olife-bot`) угадываются — только для лаборатории. Прод: ≥ 128 бит из CSPRNG.

## 4. Хранение токенов
- `gateway_dev.py`: `gateway_tokens.json` — открытые токены на диске и в памяти.
- Supervisor (этап 6): `accounts.token_hash` = SHA-256 без соли; шлюз шлёт только `token_sha` (сам токен по HTTP не идёт).
  Для **случайных** токенов ≥ 128 бит несолёный SHA-256 достаточен (словаря нет; медленный KDF нужен паролям, не токенам).
  Если когда-нибудь появятся пароли пользователей — Argon2id/scrypt на стороне supervisor, не на шлюзе.
- Rust `TokenFile`: таблица `token_sha256` (на диске только дайджесты, генерация `olife-gateway --hash-token <t>`); старый
  формат `tokens` (открытый) принимается для лаборатории и сразу превращается в дайджесты — после загрузки процесс держит
  только их. Утечка `token_sha` (логи запросов, БД) не даёт входа: шлюз хэширует то, что прислал клиент.
- Рекомендации: токен выдаёт supervisor (CSPRNG, показывается один раз), срок жизни и отзыв, ротация; «перец» (HMAC-SHA256
  с секретом supervisor вместо голого SHA-256), если токены станут короткими.

## 5. Что сделано в Rust-шлюзе сейчас (без смены протокола)
Дайджесты вместо токенов, сравнение за постоянное время, CSPRNG для challenge, лимиты неудачных входов и соединений на IP,
кадр клиента ≤ 64 КиБ проверяется по заголовку до тела, рукопожатие 5 с, медленный потребитель отключается (очередь 16 МиБ
или запись стоит > 15 с) и не блокирует мир, админ-порты только 127.0.0.1 (+ необязательный `--admin-token`), клиентский
порт по умолчанию 127.0.0.1 (`--public` — явно).

## 6. Дальше (по порядку пользы)
1. **[СДЕЛАНО, волна 4b, §7] Билет вместо токена в `Hello` (закрывает перехват и повтор, клиент меняется только паком).** Клиент по HTTPS
   (`network.post`, `verify_ssl=true`) обменивает долгий токен у supervisor на короткий билет: `{account, gateway (аудитория),
   exp = now+60 с, nonce 96 бит}` + HMAC-SHA256 ключом, общим у supervisor и шлюзов (или Ed25519 — шлюзу нужен только
   открытый ключ). base64url ≈ 80–120 символов — влезает в `token: str<128>`, **схема не меняется**. Шлюз проверяет подпись
   офлайн (supervisor может лежать), срок, аудиторию и одноразовость (кэш nonce до `exp`). Долгий токен в игровой сокет
   больше не попадает. Политику дубля сменить: второй вход не выбивает первый без свежего билета.
2. **Шифрование игрового канала в пакe (Noise NK поверх TCP):** у клиента в паке зашит статический X25519-ключ шлюза
   (pinning), рукопожатие Noise_NK (X25519 + ChaCha20-Poly1305 + BLAKE2s/SHA-256) на чистом Lua (LuaJIT, `bit`), далее
   кадры AEAD со счётчиком (повтор и подмена в середине сессии невозможны). Трафик клиента ≈ 50 КБ/с вниз — ChaCha20 в
   LuaJIT это вытянет; замерить на 0.32 (правило «проверять в движке»). Шлюз: `snow` (Rust). Это «нестандартный путь» —
   движок не трогаем.
3. **TLS 1.3 на клиентском порту** (`tokio-rustls`, ALPN `olife/1`) — сразу для не-VoxelCore клиентов (боты, утилиты,
   веб) и для варианта с TLS-прокси рядом с клиентом; для пака VoxelCore — только если движок получит TLS-сокеты
   (правки движка у нас только тестовые — это вопрос к upstream).
4. **QUIC** (`quinn`) для трансформ по UDP (ARCHITECTURE: «UDP для трансформ») — тот же барьер: у клиента есть
   `udp_connect`, но нет QUIC; реалистично — свой лёгкий UDP-канал с ключами из п.2 (Noise + AEAD + номер пакета против
   повтора), QUIC — для внешних клиентов.
5. Канал шлюз→мир между машинами: mTLS или HMAC-рукопожатие с nonce от мира (`WorldChallenge`) вместо голого секрета;
   сравнение секрета в мире — за постоянное время.
6. Мелочи: имена только ASCII `[A-Za-z0-9_-]` (сейчас Unicode alnum — гомоглифы «аdmin» с кириллицей проходят);
   в проде причины `Disconnect` 3 без внутренностей разборщика; SYN-флуд/распределённые атаки — уровень хостинга (§5).

## 7. Сделано в волне 4b (02.10, olife_w4b): билеты
**Поток.** `olife_client:auth` (пак) → `POST https://<auth>/ticket` (VoxelCore 0.32 `network.request`) → сервис билетов
`tools/olife/auth_service.py` (отдельный процесс; в лаборатории — вид `auth`) проверяет токен в БД supervisor
(`GET /sup/auth?token_sha=` демона: аккаунты, баны, журнал входов; демон лежит → файлы) → билет → клиент открывает игровой
сокет и шлёт билет в `Hello.token` (схема не менялась, `str<128>`) → шлюз проверяет **офлайн**.

**Билет** (`tools/olife/olife_ticket.py` — спецификация и эталон; Rust-близнец `/root/olife/gateway/src/ticket.rs`, общие
векторы `tools/olife/protocol/vectors/tickets.json`): `"T1." + base64url(ver u8 | exp u32 | nonce 12 B | gw u32 | alen u8 |
account | tag 16 B)`, `tag = HMAC-SHA256(K_gw, "olife-ticket-v1" ‖ тело)[:16]`, `K_gw = HMAC-SHA256(master, "olife-gw-key-v1|" ‖
id шлюза)`. Длина 59 символов для короткого имени аккаунта, максимум 127 (аккаунт ≤ 55 байт). **Почему HMAC, а не Ed25519:**
подпись Ed25519 — 64 байта = 86 символов base64, на аккаунт+nonce+срок в 128 символах остаётся ~10 байт. Ключ на шлюз
выводится из мастер-ключа: украденный ключ шлюза чеканит билеты только для этого шлюза (он и так их принимает); мастер-ключ
есть только у сервиса билетов.

**Проверка шлюзом (порядок и коды `Disconnect`):** не разбирается → 4 «bad ticket»; аудитория (`gw`) не та → **17**
«ticket for another gateway»; тег не сошёлся (сравнение за постоянное время) → **16** «bad ticket signature»; `now > exp + 2`
или `exp > now + 60 + 2` → **14** «ticket expired»; nonce уже был (кэш до exp+2 с, HashMap + очередь по сроку, предел 10⁶,
переполнен → 13) → **15** «ticket replayed»; дальше баны (список supervisor, опрос `/sup/bans` раз в 2 с, + файл), имя, дубль.
Режимы шлюза `--auth-mode tokens|tickets|both` (по умолчанию `both`, если задан `--ticket-key`): в `tickets` статический токен
→ 4 «static tokens disabled (use a ticket)» — прод-режим.

**Транспорт до сервиса билетов.** Проверено в движке 0.32 (`tools/olife/probes/probe_https.lua`): curl в 0.32 собран со
**schannel** и без параметра CA (`CURLOPT_CAINFO` не задаётся, `network.request` знает только `verify_ssl`), поэтому
самоподписанный (или любой не из хранилища Windows) сертификат с `verify_ssl=true` даёт `status 0` «SSL peer certificate or
SSH remote key was not OK»; `network.get` (без параметра verify) — то же. Ставить свой CA в хранилище Windows пользователя мы
не можем. Поэтому: dev — HTTPS с самоподписанным сертификатом (генерируется сервисом, ECDSA P-256, SAN localhost/127.0.0.1) и
`verify_ssl=false`; **запрос запечатан** к x25519-ключу сервиса, закреплённому в конфиге клиента (`--auth-pub`):
эфемерный x25519 → HKDF-SHA256 (salt `olife-auth-v1`, info `epk‖spk`) → ChaCha20-Poly1305 туда (`k_req`) и обратно
(`k_resp`), всё из `crypto` 0.32. Активный посредник без закрытого ключа сервиса не видит ни токена, ни билета (подмена
шифротекста → 400 `InvalidTag`, проверено в движке). Прод: сертификат публичного CA + `verify_ssl=true` **и** запечатывание
(`--require-sealed 1` на сервисе — открытые запросы отвергаются кодом `sealed_required`).

**Цифры (02.10, лаборатория, стоковый 0.32 headless):** выдача билета сервисом p50 14.6 мс / p95 28 мс (запечатанный запрос,
проверка в БД supervisor); первый билет бота (TLS-рукопожатие + запрос из движка) 152–153 мс по часам движка (= 3 такта цикла 20 Гц: ответ
разбирается в цикле), повторный (после reopen) 51 мс.
`olife_auth_ticket`: 11/11 — good → Welcome (+ `PacksChanged`), повтор → 15, просрочен (выдан 120 с назад) → 14, чужой шлюз → 17,
подделка тега → 16, мусор → 4, статический токен в режиме `both` → Welcome, забаненный аккаунт: сервис не выдаёт (`banned`),
выпущенный в обход билет → 5, неверный токен → `auth`; после всего законный вход проходит; мир/шлюз живы, согласованность
0 расхождений. Тот же сценарий с Rust-шлюзом (`--impl rs`): 11/11, те же коды и причины, 586 сравнено / 0 расхождений. Тесты без движка:
`tools/olife/tests/test_tickets.py` 4/4 (WSL 3.10 и Windows 3.13), Rust `cargo test` 22/22 (8 — билеты: все векторы,
чеканка байт в байт как в Python, кэш, постоянное время).

**Что осталось:** канал после рукопожатия по-прежнему открытый (перехват трафика сессии, подмена кадров в середине — §6 п.2
Noise); ключ шлюза (`--ticket-key`) читается один раз при старте (смена — перезапуск); ротация мастер-ключа — новый ключ
всем шлюзам (поле `ver` билета оставляет место для `kid`); сервис билетов — один процесс, лимит неудач 20/мин на IP.

### 7.1. Вход по нику (UX B, 16.10, olife_menu)
Сервис билетов принимает `{name, gateway}` без токена (меню клиента: ip:port + ник). Решает supervisor
(`POST /call/olife.auth_name`): синтаксис, бан, вайтлист сервера (scope = id шлюза билетов), а ник аккаунта, у которого есть
токен, ником не берётся (`nick_reserved`). Билет тот же (HMAC, ≤ 60 с, аудитория — шлюз), в Hello идёт билет, не токен.
Ограничение варианта (а): ник — не секрет; кто знает ник из вайтлиста, войдёт под ним. Для публичного сервера — пароль
(хэш в БД supervisor, лимиты попыток уже есть) или инвайт с привязкой ника (`agents/OLIFE.md` «UX B», сравнение).

## 8. Антифрод и бан по IP (16.10, olife_antifraud) — `OLIFE_ANTIFRAUD.md`
Вход по нику без пароля: ник не секрет, поэтому защищаются сервер и ники. Коды:

| где | код | когда |
|---|---|---|
| сервис билетов | `ip_banned` (+ `until`) | адрес в активном бане (адрес или CIDR, таблица `bans` супервизора) |
| сервис билетов | `rate_ip`, `rate_net` | частота билетов с IP (20/мин) / с подсети /24 (60/мин) — с автобаном IP |
| сервис билетов | `multi_account` | > 4 ников с IP за 10 мин — с автобаном IP |
| сервис билетов | `sessions_ip` | ≥ 3 живых сессий с IP |
| сервис билетов | `nick_in_use` | ник в игре с другого IP или закреплён за другим IP (grace 300 с) |
| сервис билетов | `nick_similar` / `nick_reserved` | «скелет» ника совпал с чужим / служебное имя |
| шлюзы | Disconnect 5 | бан по IP — при приёме TCP (до Hello) и на сессиях: «banned by IP <сеть> until <время>: <причина>» |
| шлюзы | Disconnect 13 | сессий с IP ≥ лимита; соединений с /24 сверх ведра (`conn_rate_net` 60/с, всплеск ×3) |
| шлюзы | **Disconnect 18** `nick_in_use` | аккаунт уже в игре с другого адреса (с того же — прежняя замена, 12) |
| шлюзы | Disconnect 4 | имя в Hello не ASCII `[A-Za-z0-9_.-]` (закрыт п.6 §6: гомоглифы) |

Канал шлюз → супервизор: `POST /call/olife.gw_sync` раз в 2 с (сессии `[account, ip, name]`, события лимитов) → баны с
причиной/сроком и настройки (`sessions_per_ip`, `conn_rate_net`, подсети, `exempt`); запасной путь — `GET /sup/bans`. Лаборатория
шлёт F2F `kick_ip {nets, reason, code, ban}`: выбить сессии и сразу внести бан в список шлюза. Автоматика (лимиты, автобаны)
не трогает сети `exempt` (по умолчанию 127.0.0.1/32).
