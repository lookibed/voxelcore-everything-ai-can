# Olife (voxelcore-0.30.6_win64_multiplayer): что это, что хотели, что есть, как делать по уму (02.10)

Источник: `D:\Prog\VoxelCore\voxelcore-0.30.6_win64_multiplayer` (README, notes/, git 27.04–01.05.2026, код паков),
полный разбор кода — в отчёте агента (сводка ниже). Движок не запускался, файлы не менялись.

## 1. Что это и что хотели
**Olife — «Garry's Mod для VoxelCore»**: сервер и клиент на самом движке (headless `VoxelCore.exe --headless --script`
+ обычный клиент), свой сокетный протокол (`sosapi/lepton`), раздача паков клиенту zip-ом при входе,
программируемые сущности-«bench»: игрок подходит с инструментом Injector, ПКМ открывает **редактор кода прямо в
игре**, код исполняется **только на сервере** в песочнице, результат (трансформы, блоки, консоль) приходит
игрокам; гравипушка для таскания сущностей; дальше по плану чат, права, voice, кастомные модели и звуки.
Схема «Архитектура платформы olife.png» целится ещё дальше: отдельный Core-сервер на Python/Go (данные, банлисты,
лимиты, мониторинг), Lua-песочница в Docker, сервер клиентов с анти-DDoS, игровой мир на VoxelCore.

## 2. Что реально есть (состояние на 01.05.2026)
Работает: сокеты, загрузчик паков, вход/выход игроков, их позиции, чанки в радиусе сервера, блоки игроков, спавн
bench и его трансформы, код в bench с ограниченным API, ~20 tps сервера. Сломано или нет: редактор и консоль
(гонки, два пространства UID, эхо статуса), gravitygun не сетевой, меню запуска нет, защита кода нет, позиции
при переподключении теряются, базовые скрипты раздаются клиентам.

Ключевые находки разбора кода (детали с file:line — в отчёте агента):
- **20 Гц у сущностей получено обходом**: ECS движка вызывает `on_update` с частотой 20/3 ≈ 6.7 Гц (`stdcomp.lua`
  делит сущности на 3 части; документация движка врёт); тики мобов перенесены в `on_world_tick`. Это правильный
  приём и единственный путь, он сохраняется до 0.34.
- **Песочница обходится одной строкой**: в окружение отдаётся сырой `entity`, `entity:get_component(...)` возвращает
  окружение компонента, у которого `__index = _G` сервера → `file`, `os`, `network`, `debug`. Библиотеки `math`/`string`
  отданы по ссылке (можно сломать серверу). Лимитов итераций/памяти/длины нет: `while true` вешает сервер.
- **Протокол**: заголовок 9 байт (маркер 28745, type, opcode, size), без лимита размера, без версии, смешанный порядок
  байт, опкоды 21/22 значат разное в разные стороны, эвристика распаковки по ключам `_`/`v`; у загрузчика свой
  заголовок. `set_nodelay` нигде не включён.
- **Авторитет размазан**: позицию игрока диктует клиент, серверный `player` не двигается (API песочницы видит игроков
  в точке спавна); блоки игроков рассылаются до валидации, отката нет; изменения мира самим сервером (жидкости) не
  синхронизируются; GravityGun двигает локальную реплику и перетирается сервером.
- **Репликация сущностей**: пакет на каждый `set_pos`, без дельт и интереса; реестр мобов только в памяти (после
  рестарта сервера новые клиенты их не видят); rot/size не сохраняются.
- **Трафик**: стартовый код bench делает `oprint` каждый тик, а `oprint` шлёт **всю консоль (до 11 КБ) всем клиентам**
  20 раз в секунду — главный источник «лагает».
- **Качество**: if-цепочки опкодов, дублирование ser/cli, мёртвые модули и конфиги (читается не тот config.json),
  `t.t.users` (nil при каждом сохранении), общий `pingTimer`, `os.clock` как RTT, отладочные `print` в горячих путях,
  миры и логи в git, движок клиента пропатчен хуком autotest в `project_client.lua`.
- **Ценное, что оставить**: QA-оркестратор (`vc_test_runner.py` 3 тыс. строк: фоновый сервер, именованные клиенты,
  маркеры `OLIFE_QA`, 19/19 PASS) — но тесты только позитивные; протокол отладчика `--dbg-server` проверен.

Что даёт движок сам (0.30.6 → 0.34): TCP и UDP (`tcp_open/udp_open`, `set_nodelay`, `recv_async`), headless с `--tps` и
детерминированным `--test`, `--stdin-cmd` (0.31+) для админ-консоли, `world.get/set_chunk_data`, `--dbg-server`.
**Встроенного мультиплеера нет ни в одной версии.** Сообщество делает **Neutron/NetRat** (клиент лежит в
`voxelcore-0.34_pre roman_donw/content/Neutron-Client`, ~9 тыс. строк): протокол из YAML-схемы с генерацией кодеков,
состояния handshake/login/in_game, KeepAlive, хэши паков, чанки, блоки, сущности с dirty-полями, инвентари, частицы,
аудио, чат, погода, RPC. Серверного пака Neutron в локальных папках нет; загрузки паков и песочницы у него нет.

## 3. Варианты, как делать по уму

### Вариант A. Чинить прототип по месту
Исправить песочницу (прокси вместо сырого `entity`, копии библиотек, бюджет), единое пространство ID, дельты консоли,
`set_nodelay`, реестр мобов, валидацию блоков. Плюс: быстро, знакомый код. Минус: архитектура (if-цепочки, глобальная
шина `api`, авторитет клиента, протокол без схемы) останется, и каждая следующая фича (чат, права, модели, звук)
будет добавлять такие же обходы. Годится только как «дожить до демо».

### Вариант B. Переписать на VoxelCore с нуля по архитектуре «сервер авторитетен», своим протоколом
Новый сервер-пак и клиент-пак, протокол из схемы (как у Neutron: описание → кодек), серверный авторитет для всего
(игроки, блоки, сущности, инвентарь), репликация снимками с интересом по чанкам, UDP для трансформов + TCP для
событий, загрузчик по манифесту с хэшами (качать только изменившееся и только клиентскую часть), песочница
по-взрослому (см. §4), логический планировщик 20 Гц вне ECS. Плюс: полностью под Olife, без чужих ограничений.
Минус: самая долгая дорога, вся сетевая база с нуля (то, что Neutron уже прошёл).

### Вариант C. Взять Neutron как сетевую базу, Olife — как слой поверх (рекомендуемый, если сервер Neutron доступен)
Neutron даёт транспорт, состояния, чанки, блоки, сущности, инвентарь, чат, RPC. Olife добавляет то, чего там нет и что
уникально: раздача/горячая загрузка паков, песочница кода сущностей, редактор и консоль в игре, Injector/гравипушка
с передачей владения, права. Плюс: экономия месяцев, живое сообщество и совместимость с их клиентом/оболочкой Quartz.
Минус: зависимость от чужого протокола и темпа; серверный пак надо достать и изучить (лицензия, качество, авторитет),
движок придётся держать в их версии (0.34 pre). Сначала — двухдневная проверка: поднять сервер Neutron с их
клиентом, прогнать чанки/блоки/сущности, посмотреть код сервера; если авторитет и качество устраивают — C, иначе B.

### Схема «Core на Python/Go в Docker» с картинки
На этом этапе преждевременна: игровой мир и так один процесс VoxelCore; данные/банлисты/мониторинг решаются
`--stdin-cmd` + файлы/SQLite + наш лаб-демон. Отдельная Lua-песочница в Docker оправдана только когда появятся
чужие игроки на публичном сервере (тогда user-код изолируется процессом с лимитами ОС, а не хуками в одном Lua-state).
Записать как цель второго этапа, не первого.

## 4. Как должен выглядеть результат (независимо от варианта)
- **Авторитет**: сервер владеет миром, игроками, сущностями, инвентарём; клиент предсказывает и откатывает.
- **Протокол**: схема с версией (YAML/JSON → кодек), один порядок байт, лимит размера кадра, ресинхронизация по
  маркеру, KeepAlive с таймаутом, отдельные каналы: TCP надёжные события, UDP трансформы/движение.
- **Репликация**: снимки с dirty-полями раз в тик, интерес по чанкам/радиусу, сетевые ID от сервера, реестр
  сущностей переживает рестарт, восстановление позиции игрока.
- **Логика 20 Гц** — свой планировщик в `on_world_tick` (ECS движка даёт 6.7 Гц на сущность).
- **Песочница пользовательского кода** (ядро Olife): прокси-объекты без `components`/`get_component`, read-only
  копии библиотек, свой `env` без `__index=_G`, `jit.off` для пользовательских функций + `debug.sethook` со
  счётчиком инструкций, корутина с бюджетом на тик, лимит памяти через `collectgarbage("count")` дельту, лимиты
  длины кода и частоты консоли, негативные тесты обхода в наборе QA. Долгосрочно — отдельный процесс/state.
- **Загрузчик**: манифест с хэшами, только клиентская часть паков, конфиг адреса один, горячая перезагрузка по
  изменению, не по таймеру.
- **Редактор/консоль**: подписка на сущность (лок на редактирование, трансляция дельт консоли подписчикам), код и
  статус хранятся на сервере и выдаются при входе.
- **Инструменты разработки**: проект `olife` в нашей лаборатории (`tools/lab/projects/olife`): виды `server`
  (headless, `--tps`, `--test` для детерминизма), `client` (тестовая сборка `--f2f`, несколько клиентов одной арендой
  группы), сценарии «сервер + N клиентов + действия по тактам», проверки по `state`-дампам (позиции, блоки,
  сущности у всех клиентов равны серверу), трафик/пакеты в отчёте, негативные тесты песочницы, нагрузка
  (боты-клиенты без рендера). Существующий QA-оркестратор переносится как проектный плагин, маркеры `OLIFE_QA`
  остаются. Golden-снимки здесь вторичны, главная метрика — согласованность состояния и задержки.

## 5. Порядок, если начинать
0. Проверка Neutron (2 дня): достать серверный пак, поднять, оценить → выбор B или C.
1. Лаборатория: проект `olife`, аренды сервер+клиенты, первый сценарий «вход двух клиентов, блок, сущность»,
   state-сравнение (3 дня; инфраструктура уже есть).
2. Протокол и авторитет (B: 2 недели; C: 1 неделя интеграции).
3. Песочница Olife с негативными тестами (1 неделя).
4. Редактор/консоль/Injector/гравипушка поверх (1–2 недели).
5. Загрузчик по манифесту, права, чат, админ-команды через `--stdin-cmd` (1 неделя).
Прототип 0.30.6 при этом — источник требований и QA-сценариев, не кода.
