## 2. Как друг находит сервер: `InfoRequest` -> `ServerInfo`

Другу нужны только строка `ip:port` (можно `ip:port#отпечаток`) и ник. Меню клиента для любого адреса, которого нет в
файле автозаполнения лаборатории, сначала спрашивает сам шлюз (фаза «Адрес и ник» экрана статуса):

1. TCP на `ip:27750`, первый кадр — **`client.InfoRequest{proto, engine}` (id 7)** вместо `Hello`.
2. Шлюз отвечает **`client.ServerInfo{proto, name, gw_id, auth_port, auth_scheme, auth_pub, packs_port, public, whitelist,
   motd}` (id 76)** и закрывает соединение **Disconnect 19** «server info sent» (не ошибка). Данные — файл `--info`
   (`server_info.json`, пишет `play_up`; шлюз перечитывает его на каждый запрос) + то, что шлюз знает сам (id шлюза билетов,
   порт паков). Без аутентификации, до любых проверок, кроме допуска соединения (бан IP, лимиты — как для `Hello`).
3. Клиент строит адреса из **хоста, который он сам набрал**, и портов из ответа: `https://<ip>:27751` (билеты),
   `http://<ip>:27752` (паки). Сервер свой внешний адрес знать не обязан. `PacksChanged.url` шлюз по-прежнему объявляет как
   `http://127.0.0.1:27752` — клиент заменяет петлевой хост на хост шлюза (`serverinfo.fix_url`; при входе через 127.0.0.1
   ничего не меняется).
4. Дальше — обычный вход UX B: запечатанный запрос билета к ключу `auth_pub`, `Hello` с билетом, манифест, sha256, мир.

Почему не «порт+1/+2»: конвенция не даёт ключ запечатывания, а без него вход по нику при `require_sealed = 1` невозможен;
`GET /info` на порту паков требует знать этот порт. Изменение протокола **аддитивное**: два новых id в `client.yaml`,
кодеки Lua/Python/Rust перегенерированы (`gen_codecs.py --lang all`, векторов 376 -> 384), оба шлюза (Rust и
`gateway_dev.py`) отвечают одинаково. Старый шлюз на `InfoRequest` отвечает Disconnect 3 — клиент тогда идёт по прежним
данным (последний сервер с этим адресом / сервис билетов из файла), а если их нет — ошибка `[no_info]` на экране статуса.

## 3. Чему доверяем и почему

| что | защищает | от чего не защищает |
|---|---|---|
| **отпечаток в приглашении** `ip:27750#ABCDEFGHIJKL` (первые 12 символов b64url ключа сервиса билетов, 72 бита) | подмену `ServerInfo` активным посредником: ключ не совпал -> `[server_key fingerprint]`, вход не идёт | если само приглашение пришло по подменённому каналу |
| **TOFU**: ключ запоминается в `config:olife_client/menu.json` (последние серверы) | подмену при следующих входах без отпечатка: `[server_key key_changed]`; «Повторить» = явное «принять новый ключ» (хост пересоздал ключи) | первый вход без отпечатка |
| **запечатанный запрос билета** (x25519 + HKDF + ChaCha20-Poly1305, §7 `OLIFE_GATEWAY_SECURITY.md`) к ключу из шага выше | чтение и подмену запроса/ответа билета; TLS сервиса билетов самоподписанный, `verify_ssl=false` (curl+schannel 0.32 без параметра CA) — TLS тут только от пассивного наблюдателя | — |
| **токен аккаунта** (только у хоста, из `export:olife_server.txt`) | никогда не запечатывается к ключу из `ServerInfo`, если он не равен ключу файла (`[server_key token_pin]`) | — |
| **билет** (HMAC, ≤ 60 с, одноразовый, аудитория = id шлюза) | повтор, чужой шлюз (коды 14–17) | — |
| **вайтлист по нику** | вход незнакомцев | ник — не секрет: кто знает ник друга из вайтлиста, войдёт под ним, пока друг не в игре (в игре — `nick_in_use`/18 с другого IP; после выхода ник 300 с закреплён за IP друга) |
| **раздача паков**: sha256 каждого файла против манифеста, 409 при изменении | порчу файлов в пути, если манифест настоящий | **манифест не подписан** и идёт по HTTP: активный посредник между другом и хостом может подсунуть свой манифест и свой Lua-код пака — это исполнение кода в VoxelCore друга (в пределах того, что движок даёт пакам: `user:`/`config:`/`world:`, `network.*`) |

Вывод для пользователя: **по LAN и через VPN (Radmin VPN, ZeroTier, Tailscale) — нормально**; через проброс портов в
интернет игровой канал и раздача паков открыты для посредника на пути (провайдер, публичный Wi-Fi друга). Отпечаток в
приглашении закрывает подмену сервиса билетов, но не паков и не игрового канала. Друг в любом случае доверяет хосту как
автору модов: паки хоста — код, который выполняется у друга.

## 4. Модель угроз публичного режима (честно)

1. **Открыто в интернет ровно три порта** (после проброса на роутере): шлюз (Rust: лимиты соединений на IP и /24, бан IP до
   `Hello`, рукопожатие 5 с, keepalive, лимиты сообщений/байт, антифрод), сервис билетов (Python `ThreadingHTTPServer`: тело
   ≤ 8 КБ, 20 неудач/мин на IP -> 429 на 30 с, лимиты частоты билетов антифрода; поток на соединение — медленный флуд
   соединений его заметно нагрузит, это слабее шлюза), раздача паков (Rust: только файлы манифеста и CAS-активы по sha256,
   409/404, без листинга).
2. **Не открыто:** admin HTTP шлюза, все F2F-порты, песочница, демон с панелью и `/call/*` — только 127.0.0.1 (сценарий
   проверяет netstat).
3. **Игровой канал не шифруется** (TCP, кадры протокола). Пассивный наблюдатель видит чат, позиции, код бенчей; активный —
   может вставлять кадры в сессию. Лечится Noise (§6 п.2 `OLIFE_GATEWAY_SECURITY.md`) — не сделано; до тех пор — VPN.
4. **Ник не секрет** (вариант (а) UX B). Пароль/инвайт — варианты (б)/(в), ждут решения пользователя.
5. **Антифрод и NAT:** все друзья за одним роутером приходят с одного внешнего IP. Лимит `sessions_per_ip` = 3 (сервис билетов
   `sessions_ip`, шлюз — Disconnect 13). Умолчание не поднимали: при 4+ друзьях из одной квартиры — `lab olife fraud set
   sessions_per_ip 6` (живая ручка, без перезапуска). `127.0.0.1` хоста — в `exempt` (лимиты и автобаны его не трогают).
   Друг из той же LAN приходит со своим LAN-адресом (192.168.x.y) — это отдельный IP для антифрода и `/players`.
6. **Внутренний порт мира слушает 0.0.0.0**: `network.tcp_open(port)` 0.32 не принимает адрес (движок не меняем). Шлюз
   доверяет миру и наоборот по общему секрету (`--secret`, по умолчанию `olife-dev-secret`) — подключившийся к порту мира
   выдал бы себя за шлюз (`Attach{account, perms}`). Поэтому пак мира (`olife_world:net`) **сразу закрывает соединение не с
   127.x** («refused non-loopback gateway connection», `net.stats.refused`); порт из пула аренд (меняется) на роутере не
   пробрасывается. Проверено: соединение с LAN-адреса хоста закрыто за 1 мс.
7. **Брандмауэр Windows.** Из LAN/интернета входящие на 27750–27752 нужно разрешить; агент правило не добавлял. Команда для
   пользователя (PowerShell/cmd от администратора, один раз):
   `netsh advfirewall firewall add rule name="Olife 27750-27752" dir=in action=allow protocol=TCP localport=27750-27752`
   (правило по портам, а не по программе: exe шлюза запускается копией из каталога аренды, сервис билетов — `python.exe`).
   Проверка лабораторией шла на LAN-адрес хоста с самого хоста — такой трафик брандмауэр не фильтрует, поэтому правило ей не
   понадобилось; реальный друг из LAN без правила получит «нет соединения со шлюзом».
8. **CGNAT:** если внешний IP по echo-сервису (`lab olife ip`) не совпадает с WAN-адресом в роутере, провайдер раздаёт один
   адрес многим — проброс не поможет, только VPN.
