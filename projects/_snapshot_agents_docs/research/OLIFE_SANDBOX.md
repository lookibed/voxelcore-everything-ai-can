# Olife: внешняя песочница пользовательских скриптов с тарификацией (исследование, 02.10.2026)

Контекст: `agents/research/OLIFE_ASSESSMENT.md`. Решение пользователя: код сущностей исполняется **вне VoxelCore**,
в отдельном сервисе-песочнице, который обменивается с процессом мира запросами API и результатами; **тарифицируется
всё** (CPU/топливо, память, вызовы API, сеть, хранилище) по пользователю и по сущности. VoxelCore остаётся
однопоточным симулятором мира; игроков принимает отдельный шлюз (сокеты + авторизация); процессами миров управляет
супервизор. Документ — исследование: код не писался, движок не запускался. Версии проверены по GitHub API/докам
на 02.10.2026; оценки производительности без ссылки помечены «оценка» — их надо подтвердить замером в лаборатории.

## 0. Коротко
- **Основной путь: Rust-сервис на wasmtime, внутри — интерпретатор Lua 5.1, собранный wasi-sdk в wasm.** Только он
  даёт одновременно детерминированное топливо до инструкции, жёсткий лимит памяти, приостановку с продолжением
  (а не только убийство), снимок/восстановление всего состояния скрипта копией линейной памяти и воспроизводимый
  прогон для тестов. Язык для пользователя — тот же Lua 5.1, что в паках VoxelCore. Цена — интерпретатор внутри wasm
  (оценка: в 1.5–3 раза медленнее нативного PUC Lua) и работа по сборке Lua под wasm с setjmp/longjmp.
- **Запасной путь: тот же сервис и тот же протокол, рантайм Luau (через `mlua` 0.12 с фичей `luau`).** Быстрее, проверен
  Roblox в огромном масштабе, песочница из коробки, `set_memory_limit` + `set_interrupt`. Слабее в части
  «тарификации до инструкции» (счёт идёт по точкам прерывания: обратные переходы циклов и вызовы) и не умеет снять
  образ VM.
- **Чего не делать:** LuaJIT + `debug.sethook` как основа (хуки не срабатывают в JIT-трассах, `jit.off` убивает смысл
  LuaJIT; изоляция — только ОС); V8/isolates (JS вместо Lua, тяжёлая сборка, тарификация по времени, не по инструкциям);
  Firecracker/gVisor как основной механизм (это внешний контур, не тарификатор).
- Мост мира и песочницы — **пакетный по тикам**: мир шлёт снимок того, что скрипту можно видеть, + события; песочница
  возвращает список действий; мир применяет и валидирует. Синхронного вызова «скрипт → мир» внутри тика нет: дорогие
  запросы (лучи, поиск сущностей, чтение блоков вне снимка) — асинхронные, ответ в следующем тике (корутина).

## 1. Требования, выведенные из решения пользователя
| # | Требование | Почему |
|---|---|---|
| R1 | CPU считается **детерминированно** (инструкции/топливо), не по часам | тарификация, честность, воспроизводимость; часы зависят от загрузки ПК |

Ключевые возможности по документации:
- **Luau** (https://luau.org/sandbox): `io`, `package` удалены, `debug` урезан как небезопасный; все библиотеки
  read-only; у каждого скрипта своё окружение с `__index` на встроенные глобалы («all scripts are isolated from each
  other»); «global interrupt mechanism … any Luau code is guaranteed to call this handler eventually» — Roblox так
  режет скрипты на 10 с в Studio; `__gc` для пользовательского кода нет. Память — свой аллокатор `lua_newstate(allocf)`
  и категории памяти (`lua_setmemcat`) для учёта по скриптам внутри одной VM. В `mlua`: `Lua::sandbox(true)`,
  `set_interrupt` (только Luau), `set_memory_limit`, `used_memory`.
- **wasmtime** (https://docs.wasmtime.dev/api/wasmtime/struct.Config.html): `consume_fuel` — «deterministically
  prevent infinitely-executing WebAssembly code»; epoch interruption — легче («up to 2–3x» быстрее fuel), но «not
  deterministic»; в async-режиме `fuel_async_yield_interval` — **уступить управление по исчерпании порции топлива и
  продолжить потом**; `StoreLimits`/`ResourceLimiter` — жёсткий лимит линейной памяти и таблиц на `Store`; pooling
  allocator — быстрый инстанс, «memories are never allowed to move» (резерв задаётся заранее). Exception-handling
  proposal — Tier 1 в Cranelift и Winch (нужен для setjmp/longjmp в Lua, см. §5).
- **QuickJS-ng**: `JS_SetInterruptHandler`, `JS_SetMemoryLimit`, `JS_SetMaxStackSize`; прерывание — по счётчику
  внутри интерпретатора (детерминированно в пределах версии), но язык — JS.
- **V8 isolates**: Cloudflare Workers — 10 мс CPU на запрос (free), 128 МБ на isolate, 1 с на глобальную область
  (https://developers.cloudflare.com/workers/platform/limits/) — всё по времени, не по инструкциям.

Итог: (b) лучший по тарификации и тестам, (a) — по скорости, старту и готовности. Оба — Lua. Мост и учёт делаются
независимыми от рантайма (трейт `ScriptRuntime`), чтобы выбор был обратимым.

### Почему не (c) как основа
LuaJIT: `debug.sethook(f, "", N)` в JIT-трассах не вызывается — бесконечный цикл, ставший трассой, хук не
остановит; `jit.off()` для пользовательского кода превращает LuaJIT в медленный интерпретатор без выигрыша. PUC Lua 5.4
с хуком — рабочая «дешёвая» схема, но изоляция держится на ОС (процесс, seccomp/cgroups или Job Objects), а
процесс на сущность не масштабируется. Годится как временная ступень в одном процессе-сервисе, не как цель.

### Почему не JS (d)
Пользователь и паки — на Lua; переход на JS ломает R5. QuickJS-ng технически годится (прерывание + лимит памяти),
V8 тарифицирует временем. Если когда-нибудь нужен JS/TS для игроков — он придёт сам через (b): QuickJS-ng или
AssemblyScript тоже компилируются в wasm и тарифицируются тем же топливом.

### (e) — внешний контур, не замена
Сервис-песочница в проде — отдельный процесс под отдельным пользователем: Linux — cgroups v2 (`memory.max`,
`cpu.max`), seccomp/landlock (никаких `open`/`connect`, кроме сокета к миру), сетевой namespace без выхода наружу;
при желании контейнер с runtime `runsc` (gVisor). Firecracker нужен только если когда-нибудь пустим **нативный** код
пользователей — для wasm/Luau избыточен. На Windows-dev — Job Object (лимит памяти/CPU-rate) или просто без него:
внутренние лимиты wasmtime/Luau работают одинаково.

## 5. Основной вариант: wasmtime + Lua 5.1 в wasm
**Сборка.** PUC Lua 5.1.5 (+ LuaBitOp как `bit`, совместимо с паками VoxelCore; без `io`/`os`/`package`/`debug`/`loadlib`,
`load`/`loadstring` только с текстовым чанком — загрузку байткода запретить: в 5.1 байткод не верифицируется) →
wasi-sdk 30 → `olife_lua.wasm` (оценка: 200–300 КБ). Lua обрабатывает ошибки через `setjmp/longjmp`: собирать с
`-mllvm -wasm-enable-sjlj -lsetjmp` (нужен exception-handling proposal — в wasmtime Tier 1) либо как C++ с
`LUAI_THROW` через исключения. **Это первый риск, проверить прототипом за день.** Импорты WASI не давать
(`wasi:clocks`, `wasi:random`, ФС — нет); единственные импорты — `host_*` из §7. Аллокатор в C — свой `l_alloc` со
счётчиком по текущей сущности (атрибуция памяти внутри VM владельца). Хэш-сид строк — константа.

**Хост.** Rust, `wasmtime` с `consume_fuel(true)`, async-конфигурация + `fuel_async_yield_interval`, pooling allocator,
модуль предкомпилирован (`Module::serialize` → `.cwasm`), состояние «Lua поднят, stdlib загружена, API-обёртки
определены» снято Wizer'ом — каждый новый инстанс стартует из готового образа памяти (CoW).

**Модель изоляции: VM (Store) на владельца, окружение на сущность.** Одна VM на сущность — это ≥ 1–2 МБ
резерва на штуку и сотни Store; VM на владельца — естественная граница доверия (скрипты одного игрока могут
ломать только друг друга), а внутри — `setfenv`-окружение и корутина на сущность. Топливо атрибутируется точно:
`store.get_fuel()` до и после вызова тика сущности. Для «опасных»/публичных объектов (чужой код на сервере
сообщества) — опция VM на сущность.

**Длинные вычисления через тики.** Тик сущности — `coroutine.resume` её обработчика. Исчерпана порция топлива:
- мягко (есть ведро) — async-yield wasmtime: исполнение замирает посреди кода и продолжается в следующем тике
  **без участия скрипта** (настоящая вытесняющая многозадачность, которую ни Luau, ни LuaJIT не дают);
- жёстко (ведро пусто дольше N тиков, или превышен потолок) — trap; VM владельца восстанавливается из последнего
  снимка памяти или перезапускается из сохранённого `state`, сущность получает статус `throttled`/`killed`.
Действия, накопленные в незавершённом тике, не применяются (тик сущности атомарен: либо `tick_end`, либо ничего).

**Снимки и персистентность.** Образ VM = линейная память + глобалы wasm: сохраняется целиком, включая корутины и
незавершённые вычисления; пригоден для повтора в тестах (тот же вход → тот же байт-в-байт результат). Образ
привязан к сборке `olife_lua.wasm` — поэтому дополнительно хранится переносимое `state` (таблица скрипта,
сериализуемая без функций, лимит размера) для миграции при обновлении интерпретатора.

**Детерминизм.** wasm детерминирован при: отсутствии часов/случайности (RNG — сид от мира на тик), канонизации NaN
(`Config::cranelift_nan_canonicalization(true)`), детерминированном relaxed-SIMD или его отключении, фиксированном
сиде хэша строк. Адреса в куче тоже детерминированы → порядок `pairs` по таблицам-ключам совпадает между прогонами.

**Связь со Spider.** Тот же `olife_lua.wasm` Spider может транслировать в Lua и выполнить внутри VoxelCore — офлайн-
режим/одиночная игра без сервиса, с тем же интерпретатором (без тарификации, либо с топливом, если Spider научить
вставлять счётчик на обратных переходах). Не для MVP, но приятная симметрия: одна семантика скриптов везде.

## 6. Запасной вариант: Luau
Тот же Rust-сервис, `mlua` с фичей `luau`, `Lua::sandbox(true)`; VM на владельца (`Lua::new` на владельца),
сущность — отдельный thread + env. `set_memory_limit` на VM; атрибуция по сущностям — категории памяти (через
сырой C-API) или выборка `used_memory` до/после. CPU: interrupt вызывается на обратных переходах и вызовах; считаем
вызовы (кроме вызванных из GC) как единицы топлива + цена API — детерминированно, но грубо (один «шаг» может стоить
и 3, и 300 инструкций). Исчерпание → ошибка «budget» из interrupt; корутина сущности не продолжается с середины —
пользователь пишет долгие вычисления явно (`yield()`/`sleep(ticks)` по API), как в Roblox `task.wait`. Персистентность —
только `state`. Плюсы: быстрее (Luau-интерпретатор быстрее PUC Lua, в 2–4 раза быстрее Lua-в-wasm — оценка), готов
сегодня, совместимость с Lua 5.1 высокая. Брать, если прототип §5 упрётся в setjmp/longjmp или скорость.

## 7. Мост мир ↔ песочница
### Транспорт
VoxelCore умеет TCP (`network.tcp_open`/`tcp_connect`, `set_nodelay`, неблокирующее чтение). Мир — клиент сервиса
по localhost-TCP (одинаково на Windows и Linux; Unix-сокет — позже). Кадр: `u32 длина | u16 тип | u32 тик | тело`,
little-endian, лимит кадра (например 4 МБ), версия протокола в рукопожатии. Тело — бинарный кодек из той же схемы,
что и основной протокол Olife (генерация кодеков), режим JSON для отладки.

### Конвейер тика (20 tps, 50 мс)
```
тик N (мир, один поток):                   сервис (параллельно, пул потоков по владельцам):
  применить TickResult(N-1)  ──────┐
  симуляция N                      │
  собрать TickInput(N) ────────────┼──► исполнить скрипты N (топливо/память/время)
  отправить, не ждать              │       └─► TickResult(N) ─► приходит к началу N+1
```
Задержка действия скрипта — **один тик** (как intents в Screeps). Мир никогда не блокируется на сервисе: не пришёл
`TickResult(N)` к началу N+1 — мир применяет его, когда придёт (с пометкой опоздания), а при отставании > K тиков
перестаёт слать входы владельцу, сервис получает `Backpressure`. Сервис упал — мир живёт, сущности «заморожены».

### TickInput (мир → песочница)
- `owners[]`: владелец, бюджеты на тик (топливо, ведро), лимиты.
- `entities[]`: `eid`, владелец, хэш кода/версия, **видимое состояние** (позиция, rot, скорость, свои поля, здоровье),
  входящие события (`touched`, `used_by`, `damaged`, `message`, `timer`), ответы на асинхронные запросы прошлого тика.
- `view`: что разрешено видеть — сущности/игроки в радиусе интереса (id, позиция, тип), блоки в малом кубе вокруг
  (дельтами к кэшу сервиса), время мира, сид RNG тика.
- Видимость задаётся миром (правами), а не скриптом: песочница физически не получает того, что не положено.

### TickResult (песочница → мир)
- по сущности: `actions[]` (`set_pos`, `set_rot`, `set_vel`, `set_block`, `spawn`, `despawn`, `play_sound`,
  `emit_particles`, `say`/`print`, `send_message(eid)`, `set_timer`), `queries[]` (асинхронные: `raycast`,
  `find_entities`, `get_blocks(box)`), `status` (`ok`/`yield`/`throttled`/`error:<текст>`/`killed`), `meter` (см. §8).
- Мир **валидирует каждое действие** (права на блок/сущность, скорость, расстояние, лимиты спавна) и отвечает в
  следующем `TickInput` списком `rejected[]` с причиной — скрипт видит отказ, тарификация считается по принятым +
  штраф за отклонённые.

### Что синхронно, что нет
- Синхронно (внутри песочницы, без похода в мир): чтение своего состояния и `view`, математика, свои таблицы,
  `state`, отправка действий в буфер.
- Асинхронно (ответ в N+1): всё, что требует мира — лучи, поиск сущностей вне `view`, чтение блоков вне куба,
  инвентари, HTTP (если когда-нибудь — через шлюз, с отдельной ценой). В скрипте выглядит синхронно:
  `local hit = world.raycast(...)` = отправить запрос + `coroutine.yield()`; ответ резюмирует корутину.
- Поэтому не нужен «RPC в середине тика», который бы сделал мир заложником медленного сервиса.

### Поток событий vs запрос/ответ
Между тиками — только пакеты на тик (TickInput/TickResult). Вне тикового цикла — служебный канал запрос/ответ:
`LoadScript`, `UnloadScript`, `Snapshot`, `Restore`, `GetMeters`, `SetLimits`, `Console(subscribe)`. Консоль
отладки идёт в мир **дельтами** и только подписчикам (лечит главный источник лагов прототипа — 11 КБ всем × 20 Гц).

## 8. Тарификация
### Единицы
- **Топливо** — wasm-инструкции (вариант b) или срабатывания interrupt (вариант a). Пользователю показываем
  «кредиты»: 1 кредит = 10 000 топлива (калибруется замером).
- **API** — таблица цен в кредитах, хранится в конфиге мира, версионируется:

| Действие/запрос | Цена (кредиты, стартовые значения) | Доп. |
|---|---|---|
| `set_pos/rot/vel` | 1 | ≤ 1 на сущность за тик, повтор перезаписывает |
| `print/say` | 1 + 1/100 байт | лимит байт/тик, дельта консоли |
| `set_timer`, `send_message` | 2 | очередь ≤ 64 на сущность |
| `get_blocks(box)` | 5 + 1/64 блока | бокс ≤ 16³ |
| `raycast` | 20 | длина ≤ 64 |
| `find_entities(radius)` | 20 + 1/результат | радиус ≤ 32 |
| `set_block` | 50 | права региона, ≤ 16/тик на владельца |
| `spawn` / `despawn` | 500 / 10 | лимит живых сущностей на владельца |
| `play_sound`/`particles` | 20 | частота на сущность |
| отклонённое миром действие | 50 % цены | против спама |
| хранение `state` | по байтам, раз в N тиков | лимит размера (например 64 КБ на сущность) |
| сеть (байты TickResult по владельцу) | по КБ | считает мир/шлюз |

### Бюджет и ведро (Screeps + Expression 2)
Каждому владельцу: `fuel_per_tick` (база), `bucket` (неиспользованное копится до `bucket_max`), `tick_cap`
(максимум за тик из ведра), `hard_cap` (потолок на одну непрерывную цепочку yield'ов). Владелец делит свой бюджет
между сущностями (по умолчанию поровну, или приоритеты). Всё — в топливе, значит одинаково на любом ПК.

### Счётчики (на сущность и сводно на владельца, за тик и накопительно)
`fuel_used`, `fuel_budget`, `bucket`, `api_calls{kind}`, `api_credits`, `actions_ok`, `actions_rejected{reason}`,
`mem_current`, `mem_peak`, `state_bytes`, `console_bytes`, `net_bytes_in/out`, `yields`, `traps`, `throttled_ticks`,
`wall_ns` (только для мониторинга, в тариф не входит). Каждые N тиков — запись в журнал (SQLite у супервизора):
`(tick, owner, eid, counters…)`; в игре — панель «расход» у редактора, как у Starfall.

### Память
Жёсткий лимит на VM владельца (`StoreLimits::memory_size`), мягкий — на сущность (счётчик аллокатора; при
превышении — ошибка в скрипте сущности, VM жива). Пик — тарифицируется как «МБ·тик» при желании.

## 9. Минимальный рабочий дизайн (MVP)
**Компоненты:** `olife-sandboxd` (Rust; трейт `ScriptRuntime` с реализациями `WasmLua` и позже `Luau`), клиентский
модуль в серверном паке VoxelCore `olife_sandbox.lua` (сбор TickInput, применение TickResult, валидация), счётчики и
журнал. Шлюз и супервизор — отдельные задачи, MVP их не требует (мир и сервис запускаются лабораторией).

```rust
trait ScriptRuntime {
    fn new_owner(&mut self, owner: OwnerId, limits: Limits) -> Result<()>;
    fn load(&mut self, owner: OwnerId, eid: EntityId, src: &str) -> Result<(), CompileError>;
    fn tick(&mut self, owner: OwnerId, input: &OwnerTickInput, budget: Budget) -> OwnerTickResult; // атомарно по сущности
    fn snapshot(&self, owner: OwnerId) -> Vec<u8>;      // WasmLua: образ памяти; Luau: state-таблицы
    fn restore(&mut self, owner: OwnerId, img: &[u8]) -> Result<()>;
    fn meters(&self, owner: OwnerId) -> Meters;
}
```
Импорты wasm-модуля (ABI песочницы): `host_input(ptr,len)` (скопировать TickInput сущности в буфер),
`host_emit(ptr,len)` (добавить действие), `host_query(ptr,len)->qid`, `host_log(ptr,len)`. Всё сериализуется
пачкой: один `host_input` и N `host_emit` на сущность за тик; никаких вызовов хоста на каждое чтение поля.

API для скрипта (Lua, как сейчас в Olife, но через прокси без доступа к движку):
`self.pos/rot/vel` (чтение), `self:move_to(v)`, `self:set_block(x,y,z,id)`, `self.state` (персистентно),
`world.raycast(o,d)` (yield), `world.entities_near(r)`, `on(event, fn)`, `sleep(ticks)`, `print(...)`.
Пользовательский код — тело `on_tick`/обработчики, как в редакторе прототипа.

Сообщения (схема): `Hello{proto, world_id}`, `SetLimits{owner, fuel_per_tick, bucket_max, tick_cap, mem_max}`,
`LoadScript{owner, eid, src, version}` → `LoadResult{ok|error}`, `TickInput{tick, seed, owners[], entities[], view}`,
`TickResult{tick, per_entity[{eid, status, actions[], queries[], meter}], per_owner_meter[]}`, `Snapshot/Restore`,
`ConsoleDelta{eid, seq, text}`, `Backpressure{owner, behind_ticks}`.

**Тесты в лаборатории** (`tools/lab/projects/olife`): негативные — `while true do end`, рекурсия до переполнения,
`string.rep` на гигабайт, попытки `load` байткода, доступ к `os/io/debug/getfenv(0)`, спам действий — каждый должен
кончиться `throttled/killed` с правильными счётчиками, мир держит 20 tps; детерминизм — один и тот же журнал
TickInput дважды → побайтно одинаковые TickResult и одинаковые `meter`; нагрузка — 500 сущностей у 50 владельцев,
время сервиса на тик и p99. Замеры — через `lab perf` на свободном ПК.

## Прототип: результаты (02.10.2026)
Код: `/root/olife/sandboxd` (локальный git-репозиторий без коммитов, вне VC_ROOT), подробно — в его `README.md`.
Движок не запускался. Замеры — на машине разработки (Ryzen 7 7435HS, WSL2) **под фоновой нагрузкой**
(load average 1.5–5.6, чужой процесс держал одно ядро): шум ±20 %, перед решением по порогу повторить через
`lab perf` на свободном ПК.

**Сборка и sjlj.** wasmtime 49.0.1 + PUC Lua 5.1.5 + LuaBitOp, wasi-sdk 30 (Linux-копия в `/root/olife/toolchain`).
`-mllvm -wasm-enable-sjlj -mllvm -wasm-use-legacy-eh=false -mexception-handling` + `-lsetjmp` заработали с
первого раза. Модуль использует стандартный EH (`try_table`/`throw`, exnref), в wasmtime он включён по
умолчанию (`wasm_exceptions`, фича `gc`). Запасной `ldo.c` без longjmp не понадобился. Модуль весит 221 КБ.
11 импортов WASI от libc определены как trap: у песочницы нет ФС, часов и случайности. Два патча Lua
(блочный `luaL_addlstring`, `string.rep` с выделением результата сразу) убирают минутные C-циклы без точек хука.

**Тарификация.** Три уровня, все в топливе wasmtime и детерминированные: (1) count-хук Lua каждые 250
VM-операций → вытеснение корутины сущности посреди кода (`throttled`, продолжение в следующем тике); внутри
C-границы — «обречена» при 4× бюджета, ошибка проходит сквозь `pcall`; (2) `fuel_async_yield_interval`:
C-код без точек хука оставляет вызов владельца приостановленным (`frozen`) до следующего тика; (3) превышение
жёсткого потолка или trap → откат VM владельца к чекпойнту (копии памяти), виновник выгружен (`killed`).
Калибровка: простая VM-операция стоит 90–170 топлива (из них 30–45 — проверка хука). Скорость против
нативного PUC 5.1: ×1.4–2.8 (пустой цикл 4.0 нс против 2.85, вызов 33 нс против 15, арифметика 17.9 нс
против 6.4). Отключение топлива скорость не меняет (в пределах шума). **1 кредит = 10 000 топлива** ≈ 60–110 простых операций ≈ 2 мкс.
Типичная сущность (движение, поворот, `entities_near` по 5 соседям, состояние) — 120 К топлива за тик, из них
21 К — фиксированная цена тика и 42 К — декодирование `view` (кандидат на ленивое декодирование).
wasmtime 49 берёт плату за `memory.copy/fill` побайтно, дыры через bulk-memory нет.

**Нагрузка: 500 сущностей = 50 владельцев × 10, один и тот же поток TickInput, мс на тик сервиса:**
| рантайм | скрипт | 1 поток: среднее / p99 | 4 потока: среднее / p99 |
|---|---|---|---|
| wasm-Lua 5.1 | typical | 11.9 / 17.9 (в более тихом прогоне 9.95) | 3.2 / 4.9 |
| Luau (mlua 0.12.1) | typical | 7.7 / 11.5 | 2.2 / 3.8 |
| wasm-Lua 5.1 | heavy | 25.3 / 29.7 | 7.2 / 10.1 |
| Luau | heavy | 15.8 / 19.3 | 4.9 / 6.7 |
Порог §11 (500 типичных сущностей ≤ 20 мс) пройден обоими рантаймами даже на одном потоке.

**Память и старт.** VM владельца wasm-Lua с 10 сущностями — 1.49 МБ линейной памяти (1 МБ из них — резерв
C-стека, его можно урезать до 256 КБ; куча Lua 180–210 КБ). Luau — 0.85–0.95 МБ. Новый владелец wasm
(копия шаблона после инициализации) создаётся за 1.9–2.4 мс, Luau — за 0.7–1.0 мс; CoW/Wizer ещё не сделан.
Загрузка сущности — 35–58 мкс.

**Негативные тесты** (`cargo test`: 13 wasm + 5 Luau; `tests/driver.py negative` на уровне протокола):
| сценарий | wasm-Lua | Luau |
|---|---|---|
| `while true do end` | `throttled`, ровно своя доля бюджета, соседи и другие владельцы `ok` | `throttled` |
| бесконечный цикл внутри `pcall` в цикле | `killed` (обречена при 4× бюджета) | `throttled` (Luau уступает сквозь `pcall`) |
| `string.rep("x", 2^30)` | `error: not enough memory`, VM жива | `error` |
| рост таблицы до лимита | `error: not enough memory`, пик ≤ `mem_max` | `error` |
| рекурсия Lua / через C | `stack overflow` / `C stack overflow`, 0 trap'ов | так же |
| бэктрекинг паттерна в C | `frozen` → `killed`, откат владельца, другой владелец каждый тик `ok` | **сервис висит** (interrupt в C не вызывается) |
| `os/io/debug/getfenv/require/load`, байткод через `loadstring`, запись в stdlib | нет / отклонено / read-only | нет / нет `loadstring` / readonly |
| 100 действий за тик | 64 принято, 36 отброшено | так же |
| детерминизм между процессами | `TickResult` и хэши памяти совпадают байт-в-байт | расходится порядок `pairs` по ключам-таблицам (адреса кучи, ASLR) |
| снимок → тики → восстановление → те же тики | идентично | образа VM нет |

**Рекомендация: GO wasmtime + Lua 5.1 в wasm** как основной рантайм. Все требования R1–R8 подтверждены
прототипом, порог скорости пройден с запасом на 4 потоках. Luau в интеграции быстрее в 1.5–1.6 раза, но не
держит три требования: зацикливание C-функции вешает весь сервис, `pairs` недетерминирован, снимка нет.
