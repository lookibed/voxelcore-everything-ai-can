# LLM на GPU стокового VoxelCore средствами пака (smollm_gpu, 11.10, агент llm_gpu)

Вопрос: можно ли считать нейросеть (Ru-Small-Instruct, Llama 94M, Q8_0 — та же модель, что пак `content/smollm` гоняет на
CPU через wasmrt) на GPU внутри **стокового** VoxelCore 0.31 / 0.32 — без правок движка, только паком: Lua, шейдер,
ассеты. Ответ: **да, вся модель (12 слоёв, логиты, argmax) за один кадр движка, логиты бит в бит с нативным C,
~44 ток/с и ~22 мс/токен prefill — в 40+ раз быстрее CPU-пути (0.93 ток/с, 904 мс/токен)** и почти как нативный C в один
поток (49 ток/с, 19.8 мс/токен).

Пак: `content/smollm_gpu` (README там же), копия — `D:\Prog\VoxelCore\voxelcore-0.32.1_win64\content\smollm_gpu`.
Подготовка данных: Spider `tests/manual/real-world-smollm-gpu/` (README там же). Сценарии:
`tools/scenarios/smollm_gpu_probe.lua` + `smollm_gpu_run.py` (пробы и замеры), `tools/scenarios/smollm_gpu_demo.lua`
(демо-страница, то же — пункт «Сценарии» → smollm_gpu). Движок не менялся.

## Как это устроено (одной картинкой)

```
weights.bin (138 МБ) --file.read_bytes--> Bytearray --Canvas:_set_data(адрес)--> 117 текстур sgw_* (RGBA 768 x rows)
токен, pos  --Lua: canvas sgw_tok (int8-эмбеддинг, масштабы, cos/sin RoPE) + region картинок-->
418 фреймов gui.create_frame (768 x H) = «страницы памяти»; в каждом 1-3 <image> с цветом-маркером #FF<режим>FF80
   движок рисует все фреймы каждый кадр в порядке своей хеш-таблицы -> роли раздаются фреймам в этом порядке
   ui.glslf пака: маркер -> вычислительный режим (COPYR, IVAL, RED_*, NORMQ2, SCORES, SM_E/N, AV, KVPUT, ARGMAX1/2 ...)
=> за один кадр: E -> 12 x (норма, QKV+RoPE, KV-кэш, внимание, WO+остаток, норма, FFN SiLU, W2+остаток) -> логиты -> argmax
assets.to_canvas(фрейм AM2):at(0,0) -> индекс токена в Lua (ждёт окончания кадра на GPU)
```

## Ответы на вопросы разведки (с числами)

Чистые замеры 11.10 19:20–19:30 (ниже «Замеры»), прошлые (04:00–04:30) — при занятой GPU (чужая аренда `gpu_gen`,
GPU 38–81 %); где цифры отличаются, приведены обе.

### 1. Чтение пикселей GPU → Lua
- 0.31 и 0.32: `assets.to_canvas(<имя текстуры фрейма>)` (id фрейма = имя текстуры, без `:`, иначе ищется атлас) —
  `glGetTexImage` в новый Canvas; 0.32 ещё `gui.screenshot(frame)` (то же по цене: 256² 0.079 мс).
- Стоимость (v031, прогон `20261011_192424`): 1×1 **0.0026 мс**, 256² **0.064 мс**, 1024² **0.73 мс**;
  `canvas:at` 0.3 мкс за вызов, цикл по 256² — 5.6 мс (86 нс/тексель); `get_data` 256² 0.088 мс, 1024² 1.84 мс;
  цикл по Bytearray 256²×4 — 0.18 мс. (Прежняя оценка «0.015 мс/тексель» для `canvas:at` — неверна, это 0.0003.)
- Байты и строки доходят как есть (узор 256² — 0/4096 расхождений, перевёрнутая ориентация — 4096: строка 0 = верх).
- **Сразу после тяжёлого кадра чтение ждёт GPU**: 1×1 после кадра с 1/8/32/128 матвеками w1 — 8/9/10/24 мс, w2 — 7/8/10/29 мс.
  Т.е. `to_canvas` синхронный: в цене токена он и есть «ожидание кадра». Логиты целиком (24576 float, 64 строки 768) —
  **18 мс на 0.31, 8 мс на 0.32**; argmax на GPU и чтение 1 текселя этого не требует.

### 2. Сколько зависимых проходов за кадр
- Все фреймы `gui.create_frame` рисуются **каждый кадр**, в порядке обхода `std::unordered_map` движка (не по имени и не
  по созданию); порядок стабилен между кадрами и запусками и одинаков на 0.31/0.32 (24 фрейма: `sg_o24 sg_o23 sg_o05 …`).
- Фрейм читает текстуру другого фрейма по имени (`<image src="<id фрейма>">`): если источник уже нарисован в этом кадре —
  видна новая версия, иначе прошлого кадра. Цепочка 24 INC в порядке отрисовки — отставание 0 на всех; в обратном —
  0,1,2…23 кадра.
- Пак узнаёт порядок пробой (раунд R: фрейм R копирует «часы», остальные — R; после R видят новое значение) —
  418 фреймов за **12–13 с**, проверка цепочкой INC (конец = часы + 418), кеш в `export:smollm_gpu_order.txt`
  (следующий запуск — проверка 2 кадра, конвейер готов за 1.7 с).

### 3. Данные на GPU
- Веса 138 МБ → 117 текстур RGBA 768 × rows (до 467 строк): `file.read_bytes` (160–260 мс) → `Canvas({768, rows})` →
  `Canvas:_set_data("<адрес>", bytes)` (memcpy из Bytearray, 3–14 мс на все) → `create_texture` (150–160 мс; при
  занятой GPU было 0.5–1.8 с). Итого **~0.2 с на 0.31 и 0.32**, куча Lua 0.5 МБ. Адрес — из `tostring(ba.bytes)`.
- Максимум текстуры 32768. Выход фрейма — RGBA8 **со смешиванием SRC_ALPHA**: данные только в RGB (3 байта на тексель),
  alpha = 1; входные canvas-текстуры дают все 4 байта, но раскладка общая — 3 байта. float32 = 2 текселя (биты 0–23, 24–31).
- Точность: GLSL float даёт деление 2 ulp, sqrt 3 ulp, exp 29 ulp от C. Через `GL_ARB_gpu_shader_fp64` (fp64 в UI-шейдере
  работает на обоих движках) деление/`sqrtf`/`1/sqrtf`/`fm_expf` (exp пака smollm)/SiLU — **4096/4096 бит в бит**.
  Произведения — без слияния в fma (как C с `-ffp-contract=off`), суммы — в том же порядке, что `model.c` (MATMUL=1).

### 4. Матвек Q8
- 768→2048 (w1) и 2048→768 (w2) слоя 0: **2048/2048 и 768/768 выходов бит в бит** с нативным C (оба режима: с fma и с
  материализованным произведением).
- Время прохода сверх пустого кадра (128 матвеков в кадре): w1 **0.038 мс**, w2 **0.061 мс** (чисто; при занятой GPU было
  0.084 / 0.097). До ~32 матвеков в кадре прирост не измерим (кадр 6.9–7.0 мс — пустой кадр движка в аренде).

### 5. Вся модель
- 418 ролей-фреймов, 979 картинок (вариант v2: матвек в два прохода — IVAL целые суммы групп в фрейм `*_IV`, затем RED_*
  свёртка по группам в фрейм выхода; сумма квадратов нормы — отдельный фрейм SS). Весь токен — **один кадр**.
- Паритет (оба движка, 11.10): логиты 24576/24576 бит в бит с C для токена 4 в pos 0 и для первого токена ответа
  промптов 1 и 2 (эталоны `data/proto/logits_*.f32` = `cmp` с `real-world-smollm/reference/logits_*.f32`); токены
  ответа **13/13, 32/32 и 26/26** (промпт 4, 93 токена, тот же, что в таблице CPU пака smollm) = `reference/generations.json`.
- Скорость: см. «Замеры». v1 (матвек одним проходом, 264 фрейма) — 20 ток/с при занятой GPU, 30 ток/с позже; v2 — 44.

## Что упирается в движок и что нужно от апстрима
1. **Фрейм перерисовывается каждый кадр** → веса копируются в страницы постоянно (~4 мс), и простаивающий экземпляр
   грузит GPU (с конвейером: 46–49 % против 25–40 % фона; картинки после работы скрываются, фреймы остаются). Нужно:
   «рисовать по требованию» (`frame.dirty`/`gui.render_frame(id)`) или удаление фрейма.
2. **Одна текстура в UI-шейдере** (`u_texture`) → вход и веса должны лежать в одной странице. Нужны 2+ сэмплера (или
   `<image src2=…>`) — копирование весов исчезнет (−4 мс, −138 МБ трафика на токен).
3. **Выход только RGBA8 со смешиванием** → 3 байта на тексель, float = 2 текселя, сборка битов в шейдере. Нужен режим
   без смешивания/float-текстура фрейма (RGBA32F) — вдвое меньше текселей и проще шейдер.
4. **Порядок отрисовки фреймов = хеш-таблица** → проба 12–13 с на 418 фреймов при первом запуске. Нужен явный порядок
   (`z`/приоритет фрейма) или упорядоченный контейнер.
5. **Фрейм не больше окна** (замечено прошлой сессией, отдельно не перепроверялось) — страницы ограничены 768 × ≤480.
6. **Синхронное чтение** (`to_canvas` ждёт кадр; логиты 8–18 мс) — нужен асинхронный readback (PBO) или чтение под-области.
7. fp64 — расширение `GL_ARB_gpu_shader_fp64`; на GPU без него бит в бит не будет (обычный float — 2–29 ulp).

## Грабли (см. LESSONS «LLM на GPU»)
- `tonumber(hex, 16)` в LuaJIT насыщается на 2^32−1: адрес `0x0209…` → 4294967295 → падение в memcpy `_set_data`;
  разбор по цифрам.
- `M.argmax()` возвращает (индекс, биты): `{ M.argmax() }` кладёт в таблицу оба — второй «токен» = биты максимума
  (1098010820…) и мусорный ответ. Нашлось в демо 11.10, исправлено.
- Пак заменяет `shaders/ui.glslf` целиком: цвет `#FF??FF80` (R=255, B=255, A=128) у любой картинки UI станет режимом
  вычисления. Меню и страницы с этим шейдером рисуются как обычно (кадры выше).

## Чат (12.10, агент llm_gpu_chat)
Сделан в самом паке `smollm_gpu` (не бэкендом пака `smollm`): «Сценарии» → smollm_gpu — страница `smollm_gpu_chat` с
раскладкой CPU-чата, «Демо» — прежние три промпта. Подробно, все числа и прогоны — `content/smollm_gpu/README.md` «Чат».
- **Токенизатор — Lua** (`modules/bpe.lua` + `unicode_tables.lua`, сгенерированы из `real-world-smollm/src/unicode_tables.h`
  стендом `real-world-smollm-gpu/chat/gen_unicode_lua.py`): не wasm-модуль CPU-пака, чтобы GPU-чат не зависел от wasmrt.
  Паритет с C (`run_native --tok-test`, сам 0 расхождений с HF): 26 фраз `tok_check.py` + 300 случайных — 0 расхождений на
  стоковом luajit (`chat/tok_lua_check.py`) и в движке v031/v032 (`smollm_gpu_check.py --tok-extra`), decode == вход.
- **Ход**: prefill — по токену за кадр с текущей позиции (как демо); первый токен ответа — argmax на GPU (режим паритета)
  или логиты целиком + семплер на Lua. Чтение LG одним `get_data` через FFI-указатель Bytearray: на 0.31 12.5–13 мс на токен —
  это ожидание кадра GPU в `glGetTexImage` (его же платит argmax), на 0.32 — 0.9–1 мс (ожидание внутри кадра); сам семплер
  0.1–0.4 мс. Итог: с семплированием 40–43 ток/с против 40–45 у argmax — top-k на GPU не нужен.
- **Продолжение генерации и KV**: позиция — параметр `set_token(token, pos)`, кэш — пары фреймов KA/KB, VA/VB, внимание
  читает строки 0..pos. Без истории — pos 0 перед каждым вопросом (строки ≥ pos не читаются, перезапись не нужна). С историей
  — следующий ход с текущей pos; между ходами картинки скрыты (`llm.idle(true)`), но копирование KA↔KB/VA↔VB оставлено:
  скрытый фрейм каждый кадр очищается, без копий кэш пропал бы; KVPUT скрыт, иначе писал бы нули очищенного QKV в строку pos.
  Проверка: 2-й ход «помнить диалог» (контекст 40 токенов) — логиты 24576/24576 бит в бит с нативным C на том же контексте
  (v031 `20261012_011517_…`, v032 `…011439_…`), токены 34/34 (`…011352_…`).
- Числа: prefill 21.1–23.5 мс/токен, генерация argmax 40.4–45.0, семплирование 40.1–43.4 ток/с на 0.31 и 0.32 — совпадает с
  демо 11.10 (39–45 ток/с, 22–23 мс/токен). При живой аренде gpu_show (`gpu_worldgen`) — 24–37 ток/с: делёж GPU.

## План доводки до пака-чата (11.10; пп. 3–5 сделаны 12.10 в самом паке, см. «Чат»)
1. **Бэкенд в `content/smollm`, переключатель «GPU/CPU»** в тулбаре страницы `smollm_chat` (по умолчанию GPU, если в
   `ui.glslf` поднялся fp64 и проба порядка прошла). Токенизатор (BPE-кодирование промпта) остаётся в wasm-модуле CPU
   (`vc.llm_*` уже отдают токены промпта) — или перенести в Lua; `forward` + argmax — `smollm_gpu:llm` (prefill по токену
   за кадр: 93 токена ≈ 2.1 с против 84 с; ответ ~40 ток/с). Сэмплирование с температурой — чтение логитов (8–18 мс)
   или top-k на GPU (ARGMAX1 → топ-k частичных).
2. Зависимость паков: `smollm` подключает `smollm_gpu` (шейдер, веса страницами); общий `data/tokenizer.bin`. Веса
   хранятся дважды (100 МБ `model_q8.bin` для CPU и 138 МБ страниц) — либо собирать страницы из `model_q8.bin` в Lua при
   загрузке (`_set_data` по смещениям, numpy-раскладку `prep_model.py` перенести в Lua), либо отдавать только страницы.
