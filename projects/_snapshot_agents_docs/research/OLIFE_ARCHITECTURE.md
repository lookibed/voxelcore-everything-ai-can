# Olife: целевая архитектура (черновик 02.10, по принципам пользователя)

Принципы (зафиксированы): пользовательские скрипты исполняются **вне VoxelCore** с учётом (тарификацией) всего;
VoxelCore — только симулятор мира (он почти однопоточный: коллизии, чанки, блоки, сущности); сокеты игроков, авторизация,
баны, рейтлимиты, анти-DDoS, логи, БД — **отдельный шлюз `sockets_auth`**, который можно разнести по регионам как
изоляты; **супервизор** управляет процессами мира и песочницы, перезапускает упавшее, знает «что последнее пришло и от
кого», и он же — админ-панель состояния всей системы. Ограничение Lua из Lua — не архитектура, а последний рубеж.
Рантайм песочницы выбирается отдельно (`OLIFE_SANDBOX.md`); здесь — границы, потоки, учёт и порядок работ.

## 1. Компоненты и границы

```
игроки (VoxelCore-клиенты)            операторы/ты
      │ TCP/UDP (внешний протокол)          │ HTTPS
      ▼                                     ▼
┌──────────────┐   внутренняя шина    ┌──────────────────┐
│ sockets_auth │◄────────────────────►│   supervisor     │  control plane: процессы, конфиг, журнал,
│  (шлюз, N шт)│                      │  (control plane) │  метрики, тарифы, админ-панель, БД
└──────┬───────┘                      └───┬──────────┬───┘
       │ сессии игроков (внутр. протокол)  │ управляет │ управляет
       ▼                                   ▼          ▼
┌──────────────┐  запросы API / события ┌──────────────┐
│  world (VC)  │◄──────────────────────►│   sandbox    │  скрипты сущностей, учёт топлива/памяти/вызовов
│ headless VC  │                        │ (внешний     │  по владельцу и сущности
│ один мир =   │                        │  рантайм)    │
│ один процесс │                        └──────────────┘
└──────────────┘
```

| Компонент | Роль | Что НЕ делает | Технология (предложение) |
|---|---|---|---|
| **sockets_auth** (шлюз) | единственная точка входа игроков: TCP/UDP-сокеты, рукопожатие, авторизация (токен/аккаунт), баны, рейтлимиты по IP/аккаунту, анти-флуд/анти-DDoS (SYN-лимиты, пер-соединение бюджет байт/пакетов), версия протокола, шифрование/подпись, журнал входов; транслирует валидные пакеты в `world` по внутреннему протоколу и обратно | не знает про блоки, чанки, скрипты | отдельный бинарник (Go или Rust), stateless кроме кэша сессий; несколько экземпляров, в т.ч. в других регионах; БД аккаунтов/банов — через supervisor или общая БД |
| **world** | авторитетный симулятор одного мира: чанки, блоки, физика, сущности, инвентарь, репликация игрокам (через шлюз), применение действий из песочницы, снимки состояния для песочницы | не слушает публичные порты, не хранит аккаунты, не исполняет чужой код | `VoxelCore.exe --headless --tps 20` + серверный пак; слушает только localhost/внутренний адрес; один процесс на мир; масштаб — миры, а не потоки |
| **sandbox** | исполняет скрипты сущностей по тикам: получает срез состояния, который владельцу разрешено видеть, возвращает список действий; считает топливо, память, число вызовов API, байты, хранилище; останавливает нарушителей без вреда остальным | не трогает движок напрямую | отдельный сервис (рантайм по `OLIFE_SANDBOX.md`); один процесс на мир или на группу владельцев; изоляция ОС поверх (Job Object/cgroups) |
| **supervisor** | поднимает/перезапускает `world` и `sandbox` (Job Objects/cgroups, health, таймауты), раздаёт конфиги и тарифы, собирает журналы и метрики (последние N пакетов на каждый процесс «что и от кого»), ведёт БД (аккаунты, баны, тарифы, счётчики, инциденты), админ-панель (состояние системы, игроки, сущности, расход, кики/баны, перезапуск), раздача паков клиентам (манифест с хэшами) | не в горячем пути пакетов игры | Python/Go-сервис; это прямое развитие нашего лаб-демона (`tools/lab`: аренды, Job Objects, журнал, история SQLite, панель) — переиспользуется |

Все внутренние каналы — только на внутренних адресах (localhost/VPN), наружу смотрит только шлюз.

## 2. Потоки данных

**Вход игрока**: клиент → шлюз (рукопожатие, токен, версия, бан-лист, лимиты) → шлюз регистрирует сессию у supervisor
(кто, откуда, когда) → шлюз открывает/использует внутреннее соединение с нужным `world` и пробрасывает сессию
(`session_id`, аккаунт, права). Разрыв/кик — шлюз закрывает, `world` получает событие.

**Игровой трафик**: клиент ⇄ шлюз ⇄ world. Шлюз: валидация формы пакета (схема, размер, частота), подсчёт байт на
аккаунт, мультиплексирование многих клиентов в одно внутреннее соединение на мир (кадры с `session_id`). World:
семантическая валидация (дальность, права, скорость действий), применение, репликация с интересом по чанкам.

**Скрипты**: каждый тик `world` собирает для `sandbox` **срез**: по каждой активной сущности-скрипту — её состояние,
разрешённое окружение (блоки/сущности в радиусе интереса, события: столкновение, использование, урон, чат), бюджет
тика. `sandbox` исполняет скрипты в пределах топлива, возвращает **действия** (set_pos/rot/size, block.set, spawn,
print/oprint, сохранить состояние) с идентификаторами сущности и владельца. `world` проверяет действия по правам и
дальности, применяет, тарифицирует (стоимость действия) и шлёт результат игрокам. Запрос-ответ в середине тика не
нужен: всё, что скрипту нужно «прочитать», приходит в срезе; «сложные» запросы (рейкаст, поиск пути) — как действия с
ответом в следующем тике. Это держит `world` однопоточным и предсказуемым: один обмен за тик, бюджет на обмен ≤ 5–10 мс.

**Раздача паков**: supervisor отдаёт клиентам манифест (хэши) и только клиентские части паков; шлюз даёт ссылку/канал;
`world` в раздаче не участвует. Горячая перезагрузка — по изменению манифеста.

**Падение**: `world` упал → supervisor знает последний принятый кадр (кольцевой журнал на входе world: время,
`session_id`, опкод, размер, хэш) и последнее действие песочницы; перезапуск с последнего сохранения; шлюз держит
сессии и показывает игрокам «мир перезапускается»; инцидент в панели с дампом. `sandbox` упал → `world` продолжает без
скриптов, супервизор перезапускает, скрипты получают событие рестарта.

## 3. Тарификация («буквально на всё»)
Единая модель счётчиков по субъекту (аккаунт/владелец) и объекту (сущность/скрипт/сессия), все пишутся в supervisor:
| Ресурс | Где считается | Единица | Лимит/тариф |
|---|---|---|---|
| CPU скрипта | sandbox | топливо/инструкции за тик (детерминированно, не wall-clock) | бюджет на тик + накопитель (как «bucket» у Screeps) |
| Память скрипта | sandbox | байты, high-water | жёсткий лимит на VM, мягкий на владельца |
| Вызовы API | world | штука × стоимость по таблице (set_pos 1, block.set 5, spawn 50, oprint 1 + байты…) | бюджет на тик и на минуту |
| Трафик игрока | шлюз | байты/пакеты в обе стороны | рейтлимит, бан за флуд |
| Трафик скрипта (консоль, печать) | world/шлюз | байты подписчикам | лимит на тик |
| Хранилище | supervisor | байты состояния скриптов, файлов, миров | квота |
| Сущности | world | штук на владельца, время жизни | квота |
| Чанки/зона | world | загруженные чанки по вине владельца | квота |
Превышение: скрипт ставится на паузу с записью причины в его консоль; злостное — владелец в карантин; всё видно в
панели. Тарифы — конфиг supervisor, применяются без перезапуска.

## 4. Как VoxelCore становится «чистым симулятором»
- Серверный пак `world`: внутренний протокол на `network.tcp_open` только localhost, схема пакетов из описания
  (кодеки сгенерированы, одна и та же схема у шлюза и у клиента), таблица опкодов, лимиты размера, версия.
- Авторитет: игроки/блоки/сущности/инвентарь — только на сервере; клиент предсказывает, сервер подтверждает/откатывает.
- Планировщик 20 Гц в `on_world_tick` (ECS движка даёт 6.7 Гц на сущность); порядок тика: входящие пакеты (≤ N за
  тик) → действия песочницы прошлого тика → физика/мир → снимки для песочницы и репликация → отправка.
- Репликация снимками с dirty-полями и интересом по чанкам, сетевые ID от сервера, реестр сущностей в сохранении.
- Никакого `loadstring` чужого кода внутри движка. Единственный «локальный» код — сам серверный пак.
- Админ-команды — `--stdin-cmd` (0.31+) от supervisor; метрики тика (мс на фазу, число сущностей/чанков) — в supervisor.
- Движок для сервера берём стоковый релиз 0.31+ (нужен `--stdin-cmd`, исправления headless); правки движка — только
  тестовые (как в AlphaMine: `--f2f` для детерминированных прогонов).

## 5. Шлюз `sockets_auth` отдельно и изолятами
- Stateless по игре, состояние — сессии и кэш банов; истина в БД supervisor (или своей реплике).
- Можно поднять несколько: по регионам (меньше задержка), для отказоустойчивости; клиент получает список шлюзов.
- Защита: лимиты соединений на IP, бюджет пакетов/байт на сессию, проверка схемы до разбора, таймауты рукопожатия,
  капча/токен при подозрении, бан-листы, журнал каждого входа. DDoS уровня сети — на уровне хостинга/прокси, шлюз
  лишь не должен падать от мусора.
- Внутренний канал шлюз→world: одно соединение на пару, мультиплекс сессий, подпись/секрет, чтобы world принимал
  только от своих шлюзов.

## 6. Supervisor = развитие лаб-демона
Уже есть: процессы в Job Objects с убийством дерева, аренды, порты, журнал JSONL, история SQLite, панель HTML,
учёт нагрузки, политика «кто что может». Добавить: роли процессов (`world`, `sandbox`, `gateway`), health/heartbeat
по внутреннему протоколу, кольцевые журналы «последние N входящих» на каждый процесс, перезапуск с бэкоффом и
сохранением, конфиг/тарифы, БД аккаунтов/банов/счётчиков, панель с живым состоянием (игроки, сущности, расход,
инциденты, кнопки кик/бан/рестарт), раздача паков по манифесту. Для production — тот же код на Linux
(cgroups вместо Job Objects), для разработки — на Windows как сейчас.

## 7. Разработка и тестирование
- Проект `olife` в лаборатории: аренды `gateway` + `world` + `sandbox` + N клиентов (тестовая сборка `--f2f`, ввод по
  протоколу), сценарии по тактам, метрика — согласованность состояния у сервера и всех клиентов, задержки,
  трафик, расход топлива; негативные тесты песочницы (побег, `while true`, память, флуд консоли) — обязательны
  в воротах; нагрузочные боты без рендера; детерминизм — `--test`-режим world и фиксированный шаг песочницы.
- Старый QA-оркестратор прототипа переносится как плагин проекта (маркеры `OLIFE_QA`).

## 7a. Рантайм песочницы (итог `OLIFE_SANDBOX.md`, 02.10)
**Основной: сервис на Rust с wasmtime (v49, Apache-2.0), внутри — PUC Lua 5.1.5 + `bit`, собранный wasi-sdk в wasm.**
Только этот вариант даёт сразу: детерминированное топливо с точностью до инструкции, жёсткий лимит памяти на VM,
приостановку кода посреди выполнения и продолжение в следующем тике, снимок состояния скрипта как копию линейной
памяти, повторяемость для тестов. Язык для игроков остаётся Lua 5.1 (диалект паков VoxelCore). Изоляция: VM на
владельца + корутина на сущность (топливо по сущности — по разнице счётчика), для публичного чужого кода — VM на
сущность. Риск: `setjmp/longjmp` в Lua требует exception-handling в wasm (`-mllvm -wasm-enable-sjlj`, Tier 1 в
wasmtime) — прототип 2–3 дня решает. Порог: 500 типичных сущностей ≤ 20 мс работы сервиса на тик на машине
разработки, иначе запасной вариант.
**Запасной: Luau (Roblox) через `mlua`** за тем же интерфейсом и протоколом: быстрее и дешевле на старте, но CPU
считается грубо (по `interrupt` на переходах циклов и вызовах), без продолжения с середины и без образа VM.
Отвергнуты как основа: LuaJIT+`sethook` (хук молчит в JIT-трассах), JS-рантаймы (ломают язык, V8 считает время),
контейнеры (это внешний контур на проде, не песочница). Мост с миром — пакетный по тикам (`TickInput` → `TickResult`),
действия применяются в следующем тике (как в Screeps), запросы (лучи, поиск) через `yield` с ответом в следующем тике.
Тариф: топливо → «кредиты», таблица цен действий (`set_pos` 1 … `spawn` 500, отклонённое 50 %), бюджет на тик +
ведро + потолки, счётчики по сущности и владельцу. Негативные тесты, детерминизм и нагрузка расписаны в документе.
Оценка: прототип 2–3 дня, замер 1–2 дня, минимальный рабочий сервис 5–7 недель одного разработчика.

## 8. Порядок работ (с учётом выбора рантайма)
1. Схема протокола (внешний клиент⇄шлюз, внутренний шлюз⇄world, world⇄sandbox) + генерация кодеков — 1 нед.
2. World-пак: авторитет, планировщик, репликация снимками, внутренний порт — 2 нед (или интеграция Neutron, см. ASSESSMENT).
3. Sandbox-сервис (wasmtime + Lua 5.1, учёт, мост, негативные тесты) — прототип 1 нед., минимальный рабочий 5–7 нед.
4. Шлюз: сессии, авторизация, лимиты, баны, мультиплекс — 1–2 нед.
5. Supervisor из лаб-демона: роли, перезапуск, журналы, БД, панель, раздача паков — 2 нед.
6. Olife-слой: Injector, редактор, консоль по подписке, гравипушка с владением, права — 2 нед.
