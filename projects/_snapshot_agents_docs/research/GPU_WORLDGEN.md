# Генерация мира на GPU стокового VoxelCore средствами пака (gpu_worldgen, 11.10, агент gpu_gen)

Вопрос: можно ли в стоковом VoxelCore, без правок движка, сделать «костыльный compute shader» для генерации мира, чтобы
шейдер считал настоящий 3D-шум, результат читался в Lua и записывался как чанки? **Ответ: да, на 0.32 и на 0.31.**
Чанк 16×256×16 обходится в ≈0.01 мс GPU и 0.58–0.60 мс Lua (чтение, разбор, кодирование, `set_chunk_data`). Это
420 чанков/с; зона load-distance 8 (193 чанка) заполняется за 0.55 с от открытия мира. Тот же шум на Lua стоит
370–660 мс/чанк, то есть GPU-путь быстрее в 600–1100 раз. Мир детерминирован по seed и одинаков на 0.31 и 0.32.

Пак: `content/gpu_worldgen` (README там же), копия — `D:\Prog\VoxelCore\voxelcore-0.32.1_win64\content\gpu_worldgen`.
Сценарии: `tools/scenarios/gpu_worldgen_world.lua` + `gpu_worldgen_run.py` (лаборатория: замеры, сверки, кадры,
детерминизм), `gpu_worldgen_play.lua` (зеркало пункта «Сценарии» → gpu_worldgen), `gpu_worldgen_reopen.lua` (сохранение).
Движок не менялся.

История: пак и сценарии написаны 11.10 03:00–04:30. Предыдущий запуск агента остановлен выключением ПК, без отчёта.
Его прогоны `artifacts\lab\runs\20261011_0416*…0430*` разобраны и вошли в этот документ. 11.10 19:40–19:46 всё
перепроверено новыми прогонами, которые перечислены ниже.

## Схема
```
on_chunk_present -> очередь -> кадр N: Canvas gpuwg_params 256x4 (serial, параметры шума, cx/cz плиток) -> update()
GUI::draw кадра N: фрейм gpuwg_fb 768x431 (RGBA8 FBO), <image> с маркером #FE03FF80 -> ui.glslf пака: 3D-шум -> коды
кадр N+1: assets.to_canvas("gpuwg_fb"):get_data() -> эхо serial совпало -> decode -> codec.encode -> world.set_chunk_data
```

## Разведка (а–г)

### а. Чтение пикселей: что возвращает и сколько стоит
- `assets.to_canvas(<id фрейма>)`: имя без `:` — это текстура, `Texture::readData` = `glGetTexImage` RGBA8. Возвращает
  Canvas с байтами FBO как есть; строка 0 — низ (gl_FragCoord.y = 0.5). Есть в 0.31 и 0.32. На 0.32 есть ещё
  `gui.screenshot(frame_id)` (`Frame::takeScreenshot`) — та же цена.
- Данные несёт только RGB: альфа выхода фрейма съедается смешиванием SRC_ALPHA. Шейдер пишет A = 255, и байты RGB
  доходят точно.
- Цена (v032, `bench.readback`, прогоны 194111/194141; 0.31 — 194217):

| | 0.32 | 0.31 |
|---|---|---|
| 256×256 `to_canvas` / `get_data` | 0.078 / 0.088–0.103 мс | 0.060 / 0.100 мс |
| 1024×1024 `to_canvas` / `get_data` | 0.76–0.79 / 2.1–2.5 мс | 0.70 / 1.90 мс |
| `gui.screenshot(frame)` 1024² | 0.77–0.79 мс | нет |
| `canvas:at` | 0.09–0.18 мкс/пиксель | 0.10–0.12 |
| окно 854×480 `gui.screenshot()` | 0.70 мс | нет |

  В конвейере чтение кадра 768×431 = 0.045 мс/чанк, `get_data` = 0.025 мс/чанк (30 чанков на чтение). Ожидания GPU нет:
  пакет читается в следующем кадре, а `serial`-эхо в отдельной строке FBO подтверждает, что прочитан нужный пакет
  (`waits 0` во всех прогонах).

### б. Свой шейдер в текстуру нужного размера
- `gui.create_frame(id, id, {W, H})` — FBO фрейма, который движок рисует каждый кадр. Пак заменяет `shaders/ui.glslf`.
  Картинка с цветом-маркером `#FE03FF80` уходит в вычислительную ветку, остальной UI рисуется как в движке. Входные
  данные — текстура Canvas 256×4: все 4 байта, слово u32 на тексель.
- **Размер ограничен окном.** `Frame::draw` ставит фрейм в `{0, viewport.y − H}` проекцией главного окна, поэтому фрейм
  больше окна обрезается (LESSONS «Порт на 0.32.1»). Пак берёт `min(окно, 2048)` по каждой оси: при окне 854×480
  это 768×431 (30 плиток), при 1408×902 — 1408×861 (110 плиток).
- Цена GPU-прохода (`bench.gpu_cost`: кадр без пакета и с полным пакетом + чтением каждый кадр, 120 кадров):
  30 плиток — кадр 6.94 → 7.24 мс, **0.010 мс/чанк** (v032, 194111/194141); на 0.31 — 0.007 мс/чанк (194217).
  110 плиток при 1408×861 — 0.072 мс/чанк (042554). Но этот прогон шёл одновременно с моделью smollm_gpu на GPU (аренда
  llm_gpu 04:00–04:30), поэтому число завышено и не сравнимо.
- 1 пиксель = 6 вокселей столба: для них шейдер считает 9 плотностей (3 лишних — правила слоёв смотрят на 3 блока
  вверх), пещеры и руду. Плотность — fbm из 5 октав, то есть 5 × 8 хэшей углов на вызов.

### в. `set_chunk_data`: формат и цена
- Формат `compressed_chunks` (одинаковый в 0.31 и 0.32): `u8 flags=1, u8 0, i32 LE длина, gzip(extrle16(raw))`, где
  raw = 65536×u16 id (индекс `(y·16+z)·16+x`) + 65536×u16 state. `modules/codec.lua` считает серии прямо по массиву id.
- Размер (194547): **670 Б gzip** в среднем, extrle16 — 1750 Б, сырые данные — 262144 Б.
- Цена в Lua: decode плитки 0.23 мс, encode (extrle16 + FNV + `compression.encode` + копия) 0.14 мс,
  `world.set_chunk_data` 0.145–0.15 мс (0.31: 0.264 / 0.207 / 0.140). Работает только на загруженном чанке
  (возвращает false, если чанк выгружен), поэтому пак ждёт `on_chunk_present`. Чанки грузит игрок.
- Движок после записи пересчитывает свет и меши (LESSONS «AlphaMine — производительность»). Это видно по кадрам первых
  секунд (таблица ниже).

### г. Хуки стокового Lua-генератора
- Документация 0.32 (`doc/ru/world-generator.md`) и `src/logic/scripting/scripting_world_generation.cpp`: скрипт
  генератора отдаёт только `generate_heightmap` (2D-карта высот), `generate_biome_parameters`, `place_structures`
  и `place_structures_wide` (структуры, `:line`, `:block` поштучно). **Хука «вернуть массив вокселей чанка» нет.**
- Скрипт генератора живёт в **отдельном Lua-состоянии** (`create_state(..., StateType::GENERATOR)`): только базовые
  библиотеки, без `gui`, `assets`, `world`, `time`. Ни фрейм, ни чтение текстуры оттуда недоступны, а генерация идёт
  в `ChunksController` движка.
- Поэтому выбран путь «стоковый генератор пустоты + перезапись по `on_chunk_present`». `generators/gpu.toml`:
  один слой `core:air`, без скрипта; движок генерирует пустой чанк почти бесплатно. Теоретический путь через
  `place_structures` → 65536 `:block` на чанк из отдельного состояния без GPU бессмысленен.

## Паритет GPU ↔ CPU
- Плотность (mode 1, 24 бит с шагом 2^-20): max |GPU−CPU| = 4.22e-6 (чанк 0,0) и 4.47e-6 (−2,2), в среднем 6.7e-7.
  Шаг квантования 9.5e-7, то есть расхождение ≈ 4 шага float32. **Знак не расходится ни в одном вокселе** из 131072.
- Коды блоков в 4 чанках (0,0; 1,0; 0,−1; −2,2): **1 из 262144** (0.00038 %), в чанке 1,0 CPU даёт камень, GPU —
  воздух. Это граница пещеры: `n1²+n2² < 0.012` во float32 против double. Результат одинаков во всех прогонах, на 0.31
  и 0.32. Допуск объясняется точностью float32 у порога. Для бит-в-бит можно перевести хэш, шум и пороги на fp64
  (`GL_ARB_gpu_shader_fp64` в `ui.glslf` работает на обоих движках, smollm_gpu). Цена не мерилась.
- Кодек: данные движка (`world.get_chunk_data` сразу после записи, FNV) одинаковы во всех GPU-прогонах
  (`0,0=4942be68 1,0=3bb5df39 0,-1=fa1dbbc9 -2,2=b3cd5144`). Через несколько секунд хэш −2,2 меняется
  (070730d0/4fa506f0/a7fba93c): дёрн под нависанием становится землёй от случайных тиков. Это поведение `base`, не пака.

## Что упирается в движок и что нужно от апстрима
1. **Хук генератора с полным массивом вокселей** (`generate_chunk(x, z) -> Bytearray/voxels`), лучше из основного
   состояния или с доступом к текстурам. Тогда не нужны ни пустой мир, ни перезапись с пересчётом света и мешей.
2. **Фрейм любого размера** (свой viewport в `Frame::draw`). Сейчас размер ограничен окном.
3. **Настоящий compute/FBO API для паков**: шейдер с uniform'ами без маркера в UI-шейдере, асинхронное чтение (PBO).
   Без него приходится заменять `ui.glslf` целиком, а это конфликтует с другими паками (smollm_gpu).
4. **`world.set_chunk_data` из несжатых id** (без extrle16 и gzip в Lua). Сейчас кодирование — 0.14 мс из 0.59.

## Что не сделано
- Биомы, деревья и структуры. Пещеры только «спагетти», без больших полостей. Руда только уголь.
- Паритет бит в бит с CPU (fp64) не делался: расходится 1 воксель на 262144.
- Чистых (не contended) замеров нет: GPU-фон ПК 15–55 % и правило `sysload` ≥ 30 %.

## RLE на GPU (13.10, агент gpu_pack2)
Задача: Lua получает готовый поток extrle16 и только копирует байты, gzip и `set_chunk_data`. Движок не менялся.

**Формат** (`src/coders/rle.cpp` `extrle::encode16`, `voxels/compressed_chunks.cpp`): 65536 u16 id в порядке
`(y·16 + z)·16 + x`, затем 65536 нулевых state; серия ≤ 16384 (счётчик 0x3FFF — запись и новая серия того же значения),
запись = заголовок `cnt` (cnt < 64) или `0x80 | cnt & 63, cnt >> 6`, затем значение (1 байт: id ≤ 255). Поэтому задание
«серии ≤ 64» в паритете с кодером не годится — серии полной длины, иначе байты (и хэши областей) другие. Прежний пак писал
gzip **сжатием движка** (`compression.encode`), а не stored-блоками, как сказано в задании.

**Цепочка** (`shaders/gpu_worldgen.glsl` «RLE на GPU», `modules/gpu.lua` `rle_*`): 7 фреймов `gc.chain` (проба порядка —
корутина в `gen.frame`, ~17 кадров при первом запуске мира), один кадр на пакет из 30 чанков (854×480):
1. код 3 — генерация (как была) + 4 верхние строки кадра — копия слов параметров (один сэмплер на картинку: всё нужное
   следующим проходам едет в кадре);
2. код 4 — деревья пресета: поверхность столба для 2–3 деревьев плитки последовательно (дерево i видит листву деревьев < i),
   тот же хэш, что `presets.make_deco`; 3. код 5 — стволы/листва в коды (12 и свободный код пресета `deco.leaf_code`);
4. код 6 — слой y (256 вокселей): число стартов серий и позиция первого; 5. код 7 — байты записей серий, начатых в слое
   (конец последней — следующий старт по статистике слоёв выше, хвост id = 0 уходит в state); 6. код 8 — префиксная сумма
   байт по слоям (≤ 255 выборок на тексель — проще и дешевле 16 проходов двоичного дерева при 256 слоях);
7. код 9 — кадр E: заголовок (serial, длина потока плитки), поток (двоичный поиск слоя по префиксу, проход по слою до
   серии, 3 байта на тексель), высоты столбцов для света (верх/низ вокселей, закрывающих небо).
Lua: эхо serial (идёт по всей цепочке — при неверном порядке фреймов только задержка), копия RGB текселей плитки в буфер
`set_chunk_data` с CRC32 (gzip stored-блок, 21 + n + 8 байт), FNV потока для хэшей области. Цикл — по байтам потока
(≈ 600–1600 текселей), не по вокселям.

**Паритет** (`rle_verify=50`, прогоны `20261012_231653…231740`): все 4 пресета — 50/50 чанков поток GPU == `codec.extrle16`
(коды генератора из кадра 1 + деревья Lua), и 50/50 «движок перекодировал записанное» (`get_chunk_data` →
`compression.decode`) == поток GPU; хэши областей `b3e5e930` / `47a776dd` / `8589c44b` / `d1b78513` во всех прогонах (v032 и
v031: `20261013_00…` `gpu_worldgen_ab.py --engine v031`, 162 / 107 ч/с по `os.clock`). Запасной путь (поток > 13824 Б) — 0.

**Числа** — таблица в README пака (раздел «RLE на GPU и свет в шейдерах»): Lua 0.59–0.77 → 0.19–0.22 мс/чанк (read 0.03–0.07,
копия+CRC 0.01–0.02, set 0.15 — это уже движок: декодирование + `prebuildSkyLight`), поток (10 с перезаписи зоны)

## Свет (13.10, агент gpu_pack2)
**Что считает движок** (исходники 0.32: `logic/ChunksController.cpp`, `lighting/Lighting.cpp`, `libworld.cpp`).
`set_chunk_data` → `integrate_chunk_client`: `lightmap.clear()` + `prebuildSkyLight` (небо 15 сверху вниз до первого блока
без `sky-light-passing`), `flags.lighted = false`. Затем `ChunksController::buildLights` (когда есть все 8 соседей; F2F
`light_chunk`): `buildSkyLight` — для каждой клетки «под крышей», пропускающей свет, заливка от соседних столбцов
(`LightSolver` S), и `onChunkLoaded(expand)` — излучатели R/G/B и границы чанка. Выключить расчёт для мира или пака нельзя:
`Lighting` создаётся всегда при игроке-клиенте (`LevelController`), настроек нет. **Можно убрать заливку неба**: пак
переопределяет у существующих блоков одно свойство (`content.json` `"blocks": ["base:stone", …]` + `blocks/base/stone.json`
`{"sky-light-passing": true}` — `ContentUnitLoader::loadDefs` берёт существующее определение и дописывает ключи). Тогда
небо 15 во всех клетках, `buildSkyLight` ничего не заводит; остаются обход чанка и граница `expand` (16384 клетки с
небом 15 → очередь решателя) и лампы. **Что нужно от апстрима**: флаг мира/генератора «без небесного света» (или Lua-API
записи lightmap) — тогда и `expand`, и `prebuildSkyLight` (в `set_chunk_data`, 0.15 мс) не нужны.

**Замер** (`light_chunk`, мс/чанк, поток): classic 0.88 → 0.64, mountains 1.42 → 0.74, caves 1.34 → 1.00 (лампы считает

  вокселей (плотность + деревья) и Lua кладёт в регион атласа `gwl_world` (512×520, у (2, 2) — самая высокая текстура);

Проверка: высоты региона == `block.get` во всех 6400 столбцах [-2..2]² каждого пресета (`light_check=2`, прогоны 12.10 ~23:43, тег v2).

- **Потолок**: `gen.cfg.frame_w/frame_h = 768/432` (было nil = окно). Цепочка RLE 768×374, 24 плитки за проход при любом окне

  опции `launch.open` файл не перекрывают (`gen.cfg_explicit`). Проверено: 1408×902 → 1408×834/99, 2048 при окне 854×480 →
  768×466/30, умолчание при окне 1408×902 → 768×374/24 (`runs\20261013_010254/010306/010319`).
- **Подгон картинки под пакет**: проход = картинки A (плитки / строки потока кадра E) и B (служебные строки), A —
  `ceil(n/tilesX)·86` строк (кадр E — `1 + n·KR`). Строки FBO [a, b) = UI-картинка y = H − b (камера UI перевёрнута, фрейм
  прижат к низу окна: `Frame::draw`). Подгон снимает 3–4 мс кадра на проходе 2048×2048 при 24 чанках (25.0/26.7 против
  29.0/29.8 мс), основное остаётся за чтением всего фрейма (`assets.to_canvas` частичного чтения не умеет): 768×432 — 8.15 мс.
- **Ошибка в паке света исправлена**: нижние высоты столбцов шейдер пишет после `n·86` текселей пакета, `gpu.rle_heightmap`
  считал от `nt` раскладки — у неполных пакетов (их большинство: в среднем 16–21 из 24) пак `gpu_worldgen_light` читал чужие байты.
- **Чанков на кадр** (`gen.cpf`, строка лога `per frame`, HUD): при ld 32 (максимум настройки 80, но ≈ 0.6 МБ ОЗУ на чанк —
  ld 80 ≈ 12 ГБ при 2–3 ГБ свободных) новый мир и полёт упираются в подачу движка — `chunks_load` 1.3–1.95 мс на пустой чанк
  в бюджете `load-speed` 32 мс ≈ 24 чанка за кадр; `raw` получает с GPU 23–24 ч/кадр при проходе 24, 99 и 336 плиток.
  Большой проход выигрывает только в перезаписи загруженных чанков (requeue/F6): 24 → 97 → 320 ч/кадр, 550 → 1270 → 2200
  записей/с, но 23 → 13 → 7 fps, и свет движка (≈ 33 чанка за кадр в том же бюджете) отстаёт: за фазу 2600 освещённых при
  768×432 против 1300 при 2048×2048.
- **Темп `frame` в полёте**: fps опускает сам движок (создание пустых чанков), темп урезает запись до 1 ч/кадр — 7–27 ч/с,
  очередь 2500–2800. Не исправлялось (поведение темпа — решение gpu_pack2); предложение — нижний предел `n_allow` ≈ подачи
  движка или fps без вклада `chunks_load`.
- Сценарий: `tools/scenarios/gpu_worldgen_throughput.lua|.py` (`--configs окно:проход,… --paces frame,raw --repeat 2 --ld 32
  --speed 160 --flight-s 20 [--requeue 1] [--fit 0]`; проход `cfgWxH` — через файл настроек, `default` — умолчание пака).

## Нижний предел записи за кадр = подача движка (13.10, главная сессия)
Тест полёта (`gpu_worldgen_throughput.py`, ld 32, 160 бл/с) показал: темп `frame` опускал запись до 1 чанка за кадр при очереди
2500 (fps ронял сам движок созданием пустых чанков, темп принимал это на свой счёт), мир впереди оставался пустым. Теперь в
`gen.lua` нижний предел чанков за кадр = EMA числа чанков, пришедших по `on_chunk_present` за кадр («подача движка», ~24 при
load-speed 32), не выше `min_per_frame = 24`. Жёсткие 24 без привязки к подаче роняли fps новой зоны ld 32 с 43 до 23 — отвергнуто.
Числа (v032, 854×480, проход 768×432, ld 32, 2 прогона, contended): полёт 20.0–20.2 ч/кадр, 386–388 ч/с, очередь 0/5 (было
1.0 ч/кадр, 7–27 ч/с, очередь 2500–2800); статика 15.3 ч/кадр, 417–421 ч/с, 27.5 fps (было 8.4 ч/кадр, 360 ч/с, 43 fps; сырой
режим 23.5 ч/кадр, 537 ч/с, 23 fps). Классика ld 8: хэш `b3e5e930` тот же, 402 ч/с от открытия, avg 51.5 fps, p95 кадра 57 мс
(contended; `/tmp`-лог прогона `gpu_worldgen_run.py --engine v032 --opts "backend=gpu;load_distance=8"`, 13.10 ~01:3x).
